First-Level Authority Approval (DL08)

1. Overview

DLISAP1 is a pseudo-conversational CICS/COBOL transaction (transaction ID DL08). It handles the first-level authority approval step of the driver’s license application workflow. It uses BMS map DLISA1M01 in mapset DLISA1 and reads and updates DB2 tables in the DLIS schema.

An authority user working at the terminal can:

Key Action Paragraph
F3 Load an application and show the candidate, license type, check results and payment details LOAD-APPLICATION
F4 Validate the authority user as an active level-1 authority VALIDATE-AUTHORITY
F1 Submit the approve (A) or reject (R) decision SUBMIT-APPROVAL1
F12 Exit the transaction PROCESS-INPUT

The decision moves the application to one of two statuses:

  • Approve (A) sets the status to A2, which forwards the application for second-level review.
  • Reject (R) sets the status to RE, which closes the application.

Either way, the decision, authority name, date and notes are written back to DLIS.LICENSE_APPLICATION.

Three preconditions must hold before a decision is recorded:

  1. Payment is completed (PAYMENT-STATUS = 'P').
  2. The authority user is active and at level 1.
  3. The application’s license type is in the authority’s authorised license types.

DLISAP1 is a single program. It has no MQ operations and writes no files, queues or external API calls. The only update it makes is to DLIS.LICENSE_APPLICATION. DLIS.CANDIDATE and DLIS.AUTHORITY_USER are read-only.

3. Inputs

3.1 Screen Fields (Map DLISA1M01)

Field Description Usage
DA1AIDI Application ID Key for the application lookup and the update
DA1AUCOI Authority user code Key for authority validation. Also written to LAST_UPDATED_BY
DA1DECI Decision (A or R) Drives the new status and the outcome message
DA1DCNTI Decision notes Written to APPROVAL_1_NOTES

3.2 CICS System Inputs

  • EIBCALEN: 0 means first entry. Any other value means re-entry after a user action.
  • EIBAID: the key pressed (PF1, PF3, PF4 or PF12). It controls the branch.
  • DFHCOMMAREA: 350 bytes, carrying the transaction context between cycles.

3.3 DB2 Inputs

Table Columns read Purpose
DLIS.LICENSE_APPLICATION LICENSE_TYPE, APPLICATION_STATUS, ELIG_CHECK_STATUS, HIST_CHECK_STATUS, PAYMENT_STATUS, PAYMENT_REFERENCE, ELIG_CHECK_NOTES, HIST_CHECK_NOTES Application details and approval gates
DLIS.CANDIDATE FIRST_NAME, LAST_NAME Candidate name for display
DLIS.AUTHORITY_USER USER_NAME, AUTHORITY_NAME, AUTHORITY_LEVEL, LIC_TYPES_AUTH Authority validation and license type authorisation

4. Processing Logic

4.1 Overall Flow

graph TD A([Start DL08]) --> B{EIBCALEN = 0?} B -- Yes --> C[INIT-SCREEN
set date, SEND MAP ERASE FREEKB] C --> R([RETURN TRANSID DL08]) B -- No --> D[Copy DFHCOMMAREA to DLIS-COMMAREA] D --> E[RECEIVE MAP DLISA1M01] E --> F{EIBAID} F -- F1 --> G[SUBMIT-APPROVAL1] F -- F3 --> H[LOAD-APPLICATION] F -- F4 --> I[VALIDATE-AUTHORITY] F -- F12 --> X([RETURN - end conversation]) F -- Other --> M[Message: USE F1 F3 F4 OR F12] G --> S[SEND MAP DATAONLY FREEKB] H --> S I --> S M --> S S --> R

Entry (MAIN-LOGIC).

  • On first entry the program runs INIT-SCREEN. It moves the first 10 characters of CURRENT-DATE to DA1DATE. It sends the map with ERASE and FREEKB, then returns with TRANSID('DL08').
  • On re-entry it copies DFHCOMMAREA to DLIS-COMMAREA and runs PROCESS-INPUT.

Dispatch (PROCESS-INPUT).

  • It receives the map and evaluates EIBAID.
  • It re-sends the map with DATAONLY and FREEKB.
  • It returns with TRANSID('DL08') and the COMMAREA.
COBOL 
IF EIBCALEN = 0
               PERFORM INIT-SCREEN
           ELSE
               MOVE DFHCOMMAREA TO DLIS-COMMAREA
               PERFORM PROCESS-INPUT
           END-IF
COBOL 
EVALUATE TRUE
               WHEN EIBAID = DFHPF1   PERFORM SUBMIT-APPROVAL1
               WHEN EIBAID = DFHPF3   PERFORM LOAD-APPLICATION
               WHEN EIBAID = DFHPF4   PERFORM VALIDATE-AUTHORITY
               WHEN EIBAID = DFHPF12  EXEC CICS RETURN END-EXEC
               OTHER
                   MOVE 'USE F1 F3 F4 OR F12' TO DA1MSG
           END-EVALUATE

4.2 Load Application (F3)

graph TD L1{DA1AIDI = ZEROS?} -- Yes --> L2[Message: ENTER APPLICATION ID] --> LX([LOAD-APP-EXIT]) L1 -- No --> L3[SELECT LICENSE_APPLICATION
JOIN CANDIDATE] L3 --> L4{SQLCODE = 100?} L4 -- Yes --> L5[Message: APPLICATION NOT FOUND] --> LX L4 -- No --> L6[STRING full name into DA1CNAMO
move fields to map] L6 --> L7[Message: APPLICATION LOADED] --> LX

The application is read with an inner join to the candidate on CANDIDATE_ID. A missing candidate therefore also gives “not found”.

COBOL 
IF DA1AIDI = ZEROS
               MOVE 'ENTER APPLICATION ID' TO DA1MSG
               GO TO LOAD-APP-EXIT
           END-IF
COBOL 
MOVE DA1AIDI TO APPLICATION-ID OF DCLDLIS-LICENSE-APPL
           EXEC SQL
               SELECT A.LICENSE_TYPE, A.APPLICATION_STATUS,
                      A.ELIG_CHECK_STATUS, A.HIST_CHECK_STATUS,
                      A.PAYMENT_STATUS,    A.PAYMENT_REFERENCE,
                      A.ELIG_CHECK_NOTES,  A.HIST_CHECK_NOTES,
                      C.FIRST_NAME, C.LAST_NAME
               INTO   :LICENSE-TYPE, :APPLICATION-STATUS,
                      :ELIG-CHECK-STATUS, :HIST-CHECK-STATUS,
                      :PAYMENT-STATUS, :PAYMENT-REFERENCE
                      OF DCLDLIS-LICENSE-APPL,
                      :ELIG-CHECK-NOTES, :HIST-CHECK-NOTES
                      OF DCLDLIS-LICENSE-APPL,
                      :FIRST-NAME, :LAST-NAME OF DCLDLIS-CANDIDATE
               FROM   DLIS.LICENSE_APPLICATION A
               JOIN   DLIS.CANDIDATE C ON A.CANDIDATE_ID = C.CANDIDATE_ID
               WHERE  A.APPLICATION_ID = :APPLICATION-ID
                                         OF DCLDLIS-LICENSE-APPL
           END-EXEC
COBOL 
STRING FIRST-NAME OF DCLDLIS-CANDIDATE DELIMITED SPACE
                  ' ' DELIMITED SIZE
                  LAST-NAME  OF DCLDLIS-CANDIDATE DELIMITED SPACE
               INTO DA1CNAMO
           MOVE LICENSE-TYPE       OF DCLDLIS-LICENSE-APPL TO DA1LTYO
           MOVE APPLICATION-STATUS OF DCLDLIS-LICENSE-APPL TO DA1ASTTO
           MOVE ELIG-CHECK-STATUS  OF DCLDLIS-LICENSE-APPL TO DA1ELIGO
           MOVE HIST-CHECK-STATUS  OF DCLDLIS-LICENSE-APPL TO DA1HISTO
           MOVE PAYMENT-STATUS     OF DCLDLIS-LICENSE-APPL TO DA1PAYO
           MOVE PAYMENT-REFERENCE  OF DCLDLIS-LICENSE-APPL TO DA1PYRFO
           MOVE ELIG-CHECK-NOTES   OF DCLDLIS-LICENSE-APPL TO DA1ELNTO
           MOVE HIST-CHECK-NOTES   OF DCLDLIS-LICENSE-APPL TO DA1HSNTO
           MOVE 'APPLICATION LOADED' TO DA1MSG.

STRING behaviour. Each name is delimited by the first space. A name with embedded spaces, such as “Mary Ann”, is truncated at the first space.

4.3 Validate Authority (F4)

graph TD V1{DA1AUCOI = SPACES?} -- Yes --> V2[Message: ENTER AUTHORITY USER CODE] --> VX([VALIDATE-AUTH-EXIT]) V1 -- No --> V3[SELECT AUTHORITY_USER
ACTIVE_STATUS A, LEVEL 1] V3 --> V4{SQLCODE = 100?} V4 -- Yes --> V5[Message: NOT FOUND OR NOT ACTIVE AT LEVEL 1] --> VX V4 -- No --> V6[Move USER-NAME then AUTHORITY-NAME to DA1AUNMO] V6 --> V7[Message: AUTHORITY USER VALIDATED] --> VX
COBOL 
MOVE DA1AUCOI TO USER-CODE OF DCLDLIS-AUTH-USER
           EXEC SQL
               SELECT USER_NAME, AUTHORITY_NAME, AUTHORITY_LEVEL,
                      LIC_TYPES_AUTH
               INTO   :USER-NAME, :AUTHORITY-NAME, :AUTHORITY-LEVEL,
                      :LIC-TYPES-AUTH OF DCLDLIS-AUTH-USER
               FROM   DLIS.AUTHORITY_USER
               WHERE  USER_CODE       = :USER-CODE OF DCLDLIS-AUTH-USER
               AND    ACTIVE_STATUS   = 'A'
               AND    AUTHORITY_LEVEL = '1'
           END-EXEC
COBOL 
MOVE USER-NAME      OF DCLDLIS-AUTH-USER TO DA1AUNMO
           MOVE AUTHORITY-NAME OF DCLDLIS-AUTH-USER TO DA1AUNMO
           MOVE 'AUTHORITY USER VALIDATED' TO DA1MSG.

The second MOVE overwrites the first, so only the authority name appears on screen.

4.4 Submit First Approval (F1)

sequenceDiagram participant U as Authority User participant P as DLISAP1 participant DB as DB2 U->>P: PF1 with App ID, User Code, Decision, Notes P->>P: Check App ID, User Code, Decision (A/R) P->>P: PERFORM LOAD-APPLICATION P->>DB: SELECT LICENSE_APPLICATION JOIN CANDIDATE DB-->>P: Application and candidate data P->>P: Message = APPLICATION LOADED? PAYMENT-STATUS = P? P->>P: PERFORM VALIDATE-AUTHORITY P->>DB: SELECT AUTHORITY_USER (active, level 1) DB-->>P: Authority name, LIC-TYPES-AUTH P->>P: Message = AUTHORITY USER VALIDATED? License type authorised? P->>P: Decision A gives status A2, R gives status RE P->>DB: UPDATE LICENSE_APPLICATION P-->>U: Outcome message on map

The checks run in a fixed order, and the first failure ends the routine through SUBMIT-A1-EXIT:

  1. Application ID is entered.
  2. Authority user code is entered.
  3. Decision is A or R.
  4. LOAD-APPLICATION runs and must return the message “APPLICATION LOADED”.
  5. PAYMENT-STATUS is P.
  6. VALIDATE-AUTHORITY runs and must return the message “AUTHORITY USER VALIDATED”.
  7. The license type is in LIC-TYPES-AUTH.
COBOL 
IF DA1AIDI = ZEROS
               MOVE 'ENTER APPLICATION ID' TO DA1MSG
               GO TO SUBMIT-A1-EXIT
           END-IF
           IF DA1AUCOI = SPACES
               MOVE 'AUTHORITY USER CODE IS REQUIRED' TO DA1MSG
               GO TO SUBMIT-A1-EXIT
           END-IF
           IF DA1DECI = SPACES OR DA1DECI NOT IN ('A','R')
               MOVE 'DECISION MUST BE A=APPROVE OR R=REJECT' TO DA1MSG
               GO TO SUBMIT-A1-EXIT
           END-IF
COBOL 
IF PAYMENT-STATUS OF DCLDLIS-LICENSE-APPL NOT = 'P'
               MOVE 'PAYMENT MUST BE COMPLETED BEFORE FIRST APPROVAL'
                   TO DA1MSG
               GO TO SUBMIT-A1-EXIT
           END-IF
COBOL 
*    Check license type authorisation
           IF DA1LTYO NOT IN LIC-TYPES-AUTH OF DCLDLIS-AUTH-USER
               MOVE 'AUTHORITY NOT AUTHORISED FOR THIS LICENSE TYPE'
                   TO DA1MSG
               GO TO SUBMIT-A1-EXIT
           END-IF

4.5 Decision and Status Transition

stateDiagram-v2 [*] --> Loaded: F3 Load application Loaded --> A2: Decision A (all checks pass) Loaded --> RE: Decision R (all checks pass) A2: A2 - Awaiting 2nd approval RE: RE - Rejected and closed A2 --> [*] RE --> [*]
COBOL 
MOVE DA1DECI TO WS-DECISION
           IF WS-DECISION = 'A'
               MOVE 'A2' TO APPLICATION-STATUS OF DCLDLIS-LICENSE-APPL
           ELSE
               MOVE 'RE' TO APPLICATION-STATUS OF DCLDLIS-LICENSE-APPL
           END-IF

4.6 Persisting the Decision

COBOL 
EXEC SQL
               UPDATE DLIS.LICENSE_APPLICATION SET
                   APPROVAL_1_STATUS    = :WS-DECISION,
                   APPROVAL_1_AUTHORITY = :AUTHORITY-NAME
                                          OF DCLDLIS-AUTH-USER,
                   APPROVAL_1_DATE      = CURRENT DATE,
                   APPROVAL_1_NOTES     = :DA1DCNTI,
                   APPLICATION_STATUS   = :APPLICATION-STATUS
                                          OF DCLDLIS-LICENSE-APPL,
                   LAST_UPDATED_DATE    = CURRENT DATE,
                   LAST_UPDATED_BY      = :DA1AUCOI
               WHERE APPLICATION_ID     = :APPLICATION-ID
                                          OF DCLDLIS-LICENSE-APPL
           END-EXEC

After the update, the final message is set:

COBOL 
IF WS-DECISION = 'A'
               MOVE 'FIRST APPROVAL RECORDED - FORWARDED FOR 2ND APPROVAL'
                   TO DA1MSG
           ELSE
               MOVE 'FIRST APPROVAL REJECTED - APPLICATION CLOSED'
                   TO DA1MSG
           END-IF.

5. Data Model

erDiagram CANDIDATE ||--o{ LICENSE_APPLICATION : "has" LICENSE_APPLICATION { int APPLICATION_ID "key" int CANDIDATE_ID "FK" string LICENSE_TYPE "1" string APPLICATION_STATUS "2" string ELIG_CHECK_STATUS "1" string ELIG_CHECK_NOTES "200" string HIST_CHECK_STATUS "1" string HIST_CHECK_NOTES "200" string PAYMENT_STATUS "1" string PAYMENT_REFERENCE "20" string APPROVAL_1_STATUS "1" string APPROVAL_1_AUTHORITY "50" date APPROVAL_1_DATE string APPROVAL_1_NOTES "200" date LAST_UPDATED_DATE string LAST_UPDATED_BY "20" } CANDIDATE { int CANDIDATE_ID "key" string FIRST_NAME "30" string LAST_NAME "30" } AUTHORITY_USER { string USER_CODE "20" string USER_NAME "60" string AUTHORITY_NAME "50" string AUTHORITY_LEVEL "1" string ACTIVE_STATUS "1" string LIC_TYPES_AUTH "3" }

AUTHORITY_USER is not joined to the other tables. It is looked up by USER_CODE, and its LIC_TYPES_AUTH list is compared with the application’s LICENSE_TYPE in program logic.

6.2 Database Update

The update is made once, when all validations in F1 pass.

Column Value
APPROVAL_1_STATUS WS-DECISION (A or R)
APPROVAL_1_AUTHORITY AUTHORITY-NAME
APPROVAL_1_DATE CURRENT DATE
APPROVAL_1_NOTES DA1DCNTI
APPLICATION_STATUS A2 or RE
LAST_UPDATED_DATE CURRENT DATE
LAST_UPDATED_BY DA1AUCOI

6.3 Transaction Control

  • After every interaction the program issues RETURN TRANSID('DL08') with DLIS-COMMAREA and LENGTH(350).
  • F12 issues RETURN with no transaction ID, which ends the conversation.
  • There is no explicit SYNCPOINT. The commit happens when the task ends with RETURN.

7. Business Rules

# Rule Condition Result
1 New vs. returning session EIBCALEN = 0 Initialise screen. Otherwise restore the COMMAREA and process input.
2 Function key routing F1, F3, F4, F12, other Run the matching action. Other keys show guidance.
3 Application identification Application ID is zero Prompt for the ID and stop.
4 Application existence SQLCODE 100 on the join “APPLICATION NOT FOUND”
5 Active level-1 authority ACTIVE_STATUS = 'A' and AUTHORITY_LEVEL = '1' Others are treated as not found.
6 Mandatory inputs Application ID, user code, decision A or R Refuse the submission if any is missing or invalid.
7 Payment completion gate PAYMENT-STATUS is not P Block both approval and rejection.
8 License type authorisation License type is not in LIC-TYPES-AUTH Block the submission.
9 Decision-to-status mapping A or R A2 or RE
10 Persistence and audit All checks pass Update the approval columns and audit fields.
11 Outcome confirmation Decision A or R Show the forwarded or closed message.

The payment gate runs before the decision is evaluated, so it also applies to rejections.

8. Constraints

8.1 Navigation and Transaction

  • Only F1, F3, F4 and F12 trigger actions. Any other key shows USE F1 F3 F4 OR F12.
  • The first send uses ERASE. Later sends use DATAONLY.
  • The COMMAREA is fixed at 350 bytes. The program does not check the length it receives.

8.2 Sequencing

  • F1 reloads the application and revalidates the authority each time. Payment status and license type are therefore current at the time of approval.
  • Success of the load and validation steps is detected by comparing DA1MSG with the exact strings “APPLICATION LOADED” and “AUTHORITY USER VALIDATED”. Changing those texts would break the flow.
  • The program does not check the current APPLICATION-STATUS before approving. It also does not check that the eligibility or history checks passed, because those values are only displayed. An already processed application could be approved again if payment is P.

8.3 Data Formats

  • LIC-TYPES-AUTH is PIC X(3), so at most three license-type codes fit.
  • The application’s LICENSE_TYPE is 1 character, and the decision is 1 character.
  • The user code is 20 characters, and the authority name is 50.
  • Approval notes are 200 characters.
  • Candidate names are truncated at the first embedded space.

9. Error Handling

9.1 Early-Exit Pattern

Each routine has a dedicated exit paragraph (LOAD-APP-EXIT, VALIDATE-AUTH-EXIT, SUBMIT-A1-EXIT). A validation failure sets DA1MSG and uses GO TO to jump to the exit. This skips the rest of the routine and any database update. The user then corrects the input and resubmits, because there is no retry or fallback logic.

graph LR F[Validation failure] --> M[Set DA1MSG] M --> G[GO TO exit paragraph] G --> S[SEND MAP DATAONLY] S --> R[RETURN TRANSID DL08]

9.2 Known Gaps

Area Behaviour
DB2 SELECT Only SQLCODE 100 is tested. Other negative codes fall through to the success path.
DB2 UPDATE SQLCODE is not checked. A success message can appear even if the update failed or affected no rows.
CICS RESP WS-RESP1 is captured on SEND MAP and RECEIVE MAP but never tested. A MAPFAIL is silently ignored.
Abends There is no HANDLE CONDITION or HANDLE ABEND. Unhandled conditions cause a default abend.
Null indicators They are defined but not checked.
Message colour and return code They are defined but not set, so errors are not highlighted.
Audit No log, queue or transient data record is written outside the DB2 update.
Display The authority name overwrites the user name in DA1AUNMO.

10. Examples

10.1 Load an Application (F3)

Input: F3, Application ID 1000000123. The row has license type C, status A1, eligibility P, history P, payment P and reference PAY-2024-0456. The candidate is John Smith.

Output: The name John Smith, license type C, status A1, the check statuses, the payment details and the message APPLICATION LOADED.

A zero ID gives ENTER APPLICATION ID. No matching row gives APPLICATION NOT FOUND.

10.2 Validate the Authority (F4)

Input: F4, user code AUTH001. The user is active, at level 1, and authorised for CMB.

Output: The message AUTHORITY USER VALIDATED, and the authority name (for example Regional Licensing Board) in DA1AUNMO.

10.3 Successful First Approval (F1, Decision A)

Input: Application 1000000123 (payment P, license type C), user AUTH001 (level 1, authorised for CMB), decision A, notes Documents verified.

Result:

  • APPROVAL_1_STATUS = A
  • APPROVAL_1_AUTHORITY = the authority name
  • APPROVAL_1_DATE = current date
  • APPROVAL_1_NOTES = Documents verified
  • APPLICATION_STATUS = A2
  • LAST_UPDATED_BY = AUTH001
  • Message: FIRST APPROVAL RECORDED - FORWARDED FOR 2ND APPROVAL

10.4 Rejection and Blocked Submissions

A rejection with decision R and notes Failed documentation sets APPROVAL_1_STATUS to R and APPLICATION_STATUS to RE. The message is FIRST APPROVAL REJECTED - APPLICATION CLOSED.

Condition Message
Payment status is N PAYMENT MUST BE COMPLETED BEFORE FIRST APPROVAL
Decision is X DECISION MUST BE A=APPROVE OR R=REJECT
License type T is not in the authority’s list AUTHORITY NOT AUTHORISED FOR THIS LICENSE TYPE
Authority user code is blank AUTHORITY USER CODE IS REQUIRED

In each blocked case the program exits through SUBMIT-A1-EXIT and makes no database update.

10.5 Navigation and Exit

  • First entry (EIBCALEN = 0): the program sends the blank map with the current date and returns to DL08.
  • Any other key, such as F2: the message is USE F1 F3 F4 OR F12.
  • F12: the program ends with EXEC CICS RETURN.
