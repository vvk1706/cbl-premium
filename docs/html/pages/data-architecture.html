Data Architecture (DB2)

1. Overview

The Driver License Information System (DLIS) uses IBM DB2 as its relational database management system to persist all data across the full lifecycle of a driver’s license application — from candidate registration through to license issuance. The schema is owned by the DLIS schema and is accessed by a suite of CICS/COBOL online transactions running under IBM z/OS.

Seven core DB2 tables underpin the system:

Table Purpose
DLIS.CANDIDATE Stores personal details of individuals applying for a driver’s license
DLIS.LICENSE_APPLICATION Tracks each application and its full workflow status
DLIS.LICENSE_FEE_SCHEDULE Holds the fee schedule for each license type
DLIS.PAYMENT Records payment transactions against applications
DLIS.ISSUED_LICENSE Stores issued license records after final approval
DLIS.AUTHORITY_USER Holds authority user records for the two-level approval workflow
DLIS.DRIVING_HISTORY Records driving incidents for each candidate

Each table is accessed by one or more CICS transactions (DL02–DL10), and data flows in a strict pipeline: a candidate is registered, an application is submitted, fees are calculated and paid, history and eligibility checks are performed, dual-authority approval is obtained, and finally the license is issued.

2. System Architecture

2.1 High-Level Component Architecture

The DLIS system is a classic z/OS online transaction processing (OLTP) architecture. CICS manages all terminal interactions using 3270 BMS maps, while DB2 provides relational data persistence. All programs are written in Enterprise COBOL, precompiled with the DB2 precompiler (DSNHPC), and bound into a single DB2 plan (DLISPLAN) under collection DLISPKG on subsystem DSN1.

2.2 Application Workflow Pipeline

All license applications flow through a mandatory multi-step pipeline. Each step is enforced by checking the APPLICATION_STATUS code in DLIS.LICENSE_APPLICATION before a transaction can proceed to the next stage.

The APPLICATION_STATUS code in DLIS.LICENSE_APPLICATION reflects each stage:

Code Meaning Set By
PE Pending — awaiting eligibility check DLISAPPL (DL03)
EC Eligibility checked — awaiting history (upstream eligibility program)
HC History checked — awaiting payment DLISHIST (DL06)
PA Payment approved — awaiting Auth 1 DLISPAY (DL07)
A2 Awaiting second authority approval DLISAP1 (DL08)
AP Fully approved — ready for issue DLISAP2 (DL09)
IS License issued DLISISSU (DL10)
RE Rejected DLISHIST, DLISAP1, or DLISAP2

3. DB2 Tables

3.1 DLIS.CANDIDATE

The CANDIDATE table is the root entity of the system. It stores personal and contact details for every individual who registers to apply for a driver’s license. Each candidate is assigned a system-generated identity column as the primary key.

3.1.1 Column Definitions

Column Type Notes
CANDIDATE_ID DECIMAL(10) Primary key, identity generated always
FIRST_NAME VARCHAR(30) Required on create
LAST_NAME VARCHAR(30) Required on create
DATE_OF_BIRTH DATE
ID_NUMBER VARCHAR(20) Unique — national ID
ADDRESS_LINE_1 VARCHAR(50)
ADDRESS_LINE_2 VARCHAR(50) Nullable
CITY VARCHAR(30)
STATE_PROVINCE VARCHAR(30)
POSTAL_CODE VARCHAR(10) Nullable
COUNTRY VARCHAR(30)
PHONE_NUMBER VARCHAR(15) Nullable
EMAIL_ADDRESS VARCHAR(60) Nullable
CREATED_DATE DATE Default: current date
CREATED_BY VARCHAR(20) Set from CICS terminal ID (EIBTRMID)
RECORD_STATUS CHAR(1) A = Active, I = Inactive

3.1.2 Programs That Access This Table

Program Transaction Operation Details
DLISCAND DL02 SELECT Duplicate national ID check before insert
DLISCAND DL02 SELECT Inquiry by CANDIDATE_ID or ID_NUMBER
DLISCAND DL02 INSERT Create new candidate (RECORD_STATUS = 'A')
DLISCAND DL02 UPDATE Update personal details
DLISCAND DL02 UPDATE Deactivate candidate (RECORD_STATUS = 'I')
DLISAPPL DL03 SELECT (JOIN) Retrieve FIRST_NAME, LAST_NAME for display
DLISHIST DL06 SELECT (JOIN) Retrieve candidate name for history check screen
DLISPAY DL07 SELECT (JOIN) Retrieve candidate name for payment screen
DLISAP1 DL08 SELECT (JOIN) Retrieve candidate name for first approval screen
DLISAP2 DL09 SELECT (JOIN) Retrieve candidate name for second approval screen
DLISISSU DL10 SELECT (JOIN) Retrieve candidate name for issuance screen

3.1.3 SQL Code Example — Insert New Candidate (DLISCAND)

COBOL 
EXEC SQL
    INSERT INTO DLIS.CANDIDATE
        (FIRST_NAME, LAST_NAME, DATE_OF_BIRTH, ID_NUMBER,
         ADDRESS_LINE_1, ADDRESS_LINE_2, CITY, STATE_PROVINCE,
         POSTAL_CODE, COUNTRY, PHONE_NUMBER, EMAIL_ADDRESS,
         RECORD_STATUS, CREATED_BY)
    VALUES
        (:FIRST-NAME, :LAST-NAME, :DATE-OF-BIRTH, :ID-NUMBER,
         :ADDRESS-LINE-1, :ADDRESS-LINE-2, :CITY, :STATE-PROVINCE,
         :POSTAL-CODE, :COUNTRY, :PHONE-NUMBER, :EMAIL-ADDRESS,
         'A', :CREATED-BY)
END-EXEC

After the insert, the generated CANDIDATE_ID is retrieved using:

COBOL 
EXEC SQL
    SELECT IDENTITY_VAL_LOCAL()
    INTO :CANDIDATE-ID
    FROM SYSIBM.SYSDUMMY1
END-EXEC

3.2 DLIS.LICENSE_APPLICATION

The LICENSE_APPLICATION table is the central table of the DLIS system. It is the only table written to or read by every workflow transaction. It tracks the full lifecycle of an application, including the results of all check stages, payment, and both approval levels.

3.2.1 Column Definitions

Column Type Notes
APPLICATION_ID DECIMAL(10) Primary key, identity generated
CANDIDATE_ID DECIMAL(10) Foreign key → DLIS.CANDIDATE
LICENSE_TYPE CHAR(1) L = Learner, P = Probation, O = Open
APPLICATION_DATE DATE Date application submitted
APPLICATION_STATUS CHAR(2) Workflow state (PE/EC/HC/PA/A2/AP/IS/RE)
ELIG_CHECK_STATUS CHAR(1) P = Pass, F = Fail
ELIG_CHECK_DATE DATE
ELIG_CHECK_NOTES VARCHAR(200)
HIST_CHECK_STATUS CHAR(1) P = Pass, F = Fail
HIST_CHECK_DATE DATE
HIST_CHECK_NOTES VARCHAR(200)
PAYMENT_STATUS CHAR(1) P = Paid
PAYMENT_REFERENCE VARCHAR(20)
APPROVAL_1_STATUS CHAR(1) A = Approved, R = Rejected
APPROVAL_1_AUTHORITY VARCHAR(50) Name of first approving authority
APPROVAL_1_DATE DATE
APPROVAL_1_NOTES VARCHAR(200)
APPROVAL_2_STATUS CHAR(1) A = Approved, R = Rejected
APPROVAL_2_AUTHORITY VARCHAR(50) Name of second approving authority
APPROVAL_2_DATE DATE
APPROVAL_2_NOTES VARCHAR(200)
REJECTION_REASON VARCHAR(300)
CREATED_DATE DATE
LAST_UPDATED_DATE DATE
CREATED_BY VARCHAR(20) CICS terminal ID
LAST_UPDATED_BY VARCHAR(20) Updated by each workflow step

3.2.2 Programs That Access This Table

Program Transaction Operation Details
DLISAPPL DL03 SELECT COUNT Duplicate open-application check
DLISAPPL DL03 INSERT Create new application (STATUS = 'PE')
DLISSTAT DL04 SELECT Full status inquiry by APPLICATION_ID
DLISHIST DL06 SELECT (JOIN) Load application + candidate for history check
DLISHIST DL06 SELECT Re-read ELIG_CHECK_STATUS before history check
DLISHIST DL06 UPDATE Write HIST_CHECK_STATUS, HIST_CHECK_NOTES, APPLICATION_STATUS
DLISPAY DL07 SELECT (JOIN) Load application + candidate for payment screen
DLISPAY DL07 UPDATE Set PAYMENT_STATUS = 'P', APPLICATION_STATUS = 'PA'
DLISAP1 DL08 SELECT (JOIN) Load application + candidate for first approval
DLISAP1 DL08 UPDATE Write APPROVAL_1_* fields, set APPLICATION_STATUS to A2 or RE
DLISAP2 DL09 SELECT (JOIN) Load application + candidate for second approval
DLISAP2 DL09 UPDATE Write APPROVAL_2_* fields, set APPLICATION_STATUS to AP or RE
DLISISSU DL10 SELECT (JOIN) Load application + candidate for issuance
DLISISSU DL10 UPDATE Set APPLICATION_STATUS = 'IS', LAST_UPDATED_BY

3.2.3 SQL Code Example — Insert New Application (DLISAPPL)

COBOL 
EXEC SQL
    INSERT INTO DLIS.LICENSE_APPLICATION
        (CANDIDATE_ID, LICENSE_TYPE, APPLICATION_STATUS,
         CREATED_BY, LAST_UPDATED_BY)
    VALUES
        (:CANDIDATE-ID, :LICENSE-TYPE, 'PE',
         :CREATED-BY, :CREATED-BY)
END-EXEC

3.2.4 SQL Code Example — History Check Update (DLISHIST)

COBOL 
EXEC SQL
    UPDATE DLIS.LICENSE_APPLICATION
    SET HIST_CHECK_STATUS  = :WS-HISTORY-STATUS,
        HIST_CHECK_DATE    = CURRENT DATE,
        HIST_CHECK_NOTES   = :WS-HIST-FAIL-MSG,
        APPLICATION_STATUS = :APPLICATION-STATUS,
        LAST_UPDATED_DATE  = CURRENT DATE,
        LAST_UPDATED_BY    = :EIBTRMID
    WHERE APPLICATION_ID   = :APPLICATION-ID
END-EXEC

3.3 DLIS.LICENSE_FEE_SCHEDULE

The LICENSE_FEE_SCHEDULE table stores the applicable fees for each license type. It is read-only at the application level — no DLIS transaction inserts or updates it. The table supports effective-date and expiry-date filtering so that fee changes can be scheduled in advance.

3.3.1 Column Definitions

Column Type Notes
LICENSE_TYPE CHAR(1) L, P, or O
FEE_TYPE CHAR(2) IF = Initial Fee
FEE_AMOUNT DECIMAL(10,2) Monetary amount
CURRENCY_CODE CHAR(3) e.g. USD
ACTIVE_STATUS CHAR(1) A = Active
EFFECTIVE_DATE DATE Fee is valid from this date
EXPIRY_DATE DATE Nullable — null means no expiry

3.3.2 Programs That Access This Table

Program Transaction Operation Details
DLISAPPL DL03 SELECT Retrieve FEE_AMOUNT, CURRENCY_CODE for display (F5 — Calculate Fee)
DLISPAY DL07 SELECT Retrieve active initial fee for the license type before recording payment

3.3.3 SQL Code Example — Fee Schedule Lookup (DLISAPPL / DLISPAY)

COBOL 
EXEC SQL
    SELECT FEE_AMOUNT, CURRENCY_CODE
    INTO   :FEE-AMOUNT, :CURRENCY-CODE
    FROM   DLIS.LICENSE_FEE_SCHEDULE
    WHERE  LICENSE_TYPE   = :LICENSE-TYPE
    AND    FEE_TYPE        = 'IF'
    AND    ACTIVE_STATUS   = 'A'
    AND    EFFECTIVE_DATE <= CURRENT DATE
    AND    (EXPIRY_DATE IS NULL OR EXPIRY_DATE >= CURRENT DATE)
    FETCH FIRST 1 ROW ONLY
END-EXEC

3.4 DLIS.PAYMENT

The PAYMENT table records each payment transaction made against a license application. A single application should have at most one payment row (duplicate payment is blocked by DLISPAY). The payment ID is a DB2-generated identity column.

PAYMENT_AMOUNT DECIMAL(10,2) Amount taken from fee schedule
PAYMENT_METHOD CHAR(2) CC, DC, EF, CS, or CH
PAYMENT_REFERENCE VARCHAR(30) Bank/authorisation reference
PAYMENT_STATUS CHAR(1) S = Successful
LICENSE_TYPE CHAR(1) License type at time of payment
FEE_TYPE CHAR(2) Always IF (Initial Fee)
RECEIPT_NUMBER VARCHAR(20) Constructed as RCP + date + application ID
PROCESSED_BY VARCHAR(20) Operator ID who recorded the payment

Program Transaction Operation Details

3.5 DLIS.ISSUED_LICENSE

The ISSUED_LICENSE table stores the physical license record created at the end of the workflow. It is only populated after an application reaches APPLICATION_STATUS = 'AP'. It is also queried by the status inquiry transaction (DL04) to display license number and expiry to clerks.

3.5.1 Column Definitions

Column Type Notes
LICENSE_ID DECIMAL(10) Primary key
APPLICATION_ID DECIMAL(10) Foreign key → DLIS.LICENSE_APPLICATION
CANDIDATE_ID DECIMAL(10) Foreign key → DLIS.CANDIDATE
LICENSE_NUMBER VARCHAR(20) Built from type prefix + vehicle class + IDs
LICENSE_TYPE CHAR(1) L, P, or O
ISSUE_DATE DATE DB2 CURRENT DATE at time of insert
EXPIRY_DATE VARCHAR(10) Calculated: +1/+2/+5 years by license type
LICENSE_STATUS CHAR(1) Always A (Active) on insert
VEHICLE_CLASS CHAR(2) A, B, C, or D
RESTRICTIONS VARCHAR(200) Optional text entered by issuing officer
DEMERIT_BALANCE INTEGER Always 12 on insert
ISSUED_BY_AUTH VARCHAR(50) Issuing authority entered by officer
ISSUED_BY_OFFICER VARCHAR(50) Issuing officer entered by officer
RENEWAL_COUNT INTEGER Number of renewals
PREV_LICENSE_ID INTEGER Prior license reference
NOTES VARCHAR(300)

3.5.2 Programs That Access This Table

Program Transaction Operation Details
DLISSTAT DL04 SELECT Retrieve LICENSE_NUMBER, EXPIRY_DATE when APPLICATION_STATUS = 'IS'
DLISISSU DL10 INSERT Create issued license record after final approval

3.5.3 SQL Code Example — Insert Issued License (DLISISSU)

COBOL

    INSERT INTO DLIS.ISSUED_LICENSE

END-EXEC

3.6 DLIS.AUTHORITY_USER

The AUTHORITY_USER table is the authority user registry used by both approval transactions. It controls who may approve a license application and at what level. Crucially, the second approval transaction (DL09) enforces segregation of duties by comparing the second approver’s AUTHORITY_NAME with the first approver’s authority stored in LICENSE_APPLICATION.APPROVAL_1_AUTHORITY.

3.6.1 Column Definitions

Column Type Notes
USER_CODE VARCHAR(20) Primary key — entered by approver on screen
USER_NAME VARCHAR(60) Display name
AUTHORITY_NAME VARCHAR(50) Organisation name — used in segregation check
AUTHORITY_LEVEL CHAR(1) 1 = First approver, 2 = Second approver
ACTIVE_STATUS CHAR(1) A = Active
LIC_TYPES_AUTH CHAR(3) License types this authority may approve

3.6.2 Programs That Access This Table

Program Transaction Operation Details
DLISAP1 DL08 SELECT Validate approver: ACTIVE_STATUS = 'A' AND AUTHORITY_LEVEL = '1'
DLISAP2 DL09 SELECT Validate approver: ACTIVE_STATUS = 'A' AND AUTHORITY_LEVEL = '2'

3.6.3 SQL Code Example — Authority Validation (DLISAP1 / DLISAP2)

COBOL 
EXEC SQL
    SELECT USER_NAME, AUTHORITY_NAME, AUTHORITY_LEVEL, LIC_TYPES_AUTH
    INTO   :USER-NAME, :AUTHORITY-NAME,
           :AUTHORITY-LEVEL, :LIC-TYPES-AUTH
    FROM   DLIS.AUTHORITY_USER
    WHERE  USER_CODE      = :USER-CODE
    AND    ACTIVE_STATUS  = 'A'
    AND    AUTHORITY_LEVEL = '1'
END-EXEC

3.7 DLIS.DRIVING_HISTORY

The DRIVING_HISTORY table stores driving incidents for each candidate. It is read during the history check (DL06) via a DB2 cursor, ordered by incident date descending. The driving history check evaluates three pass/fail criteria derived from this table.

3.7.1 Column Definitions

Column Type Notes
HISTORY_ID INTEGER Primary key
CANDIDATE_ID DECIMAL(10) Foreign key → DLIS.CANDIDATE
INCIDENT_DATE VARCHAR(10) Date of incident
INCIDENT_TYPE CHAR(2) e.g. SU = Suspension, DQ = Disqualification, SP = Speed
INCIDENT_DESC VARCHAR(300) Description
DEMERIT_POINTS INTEGER Accumulated for threshold check (limit: 12)
FINE_AMOUNT DECIMAL(10,2) Fine associated with the incident
FINE_PAID_STATUS CHAR(1) Y = Paid, N = Unpaid
SUSP_START_DATE VARCHAR(10)
SUSP_END_DATE VARCHAR(10) Blank = open-ended suspension
COURT_CASE_NUMBER VARCHAR(20)
RECORDED_BY_AUTH VARCHAR(50)
RECORD_STATUS CHAR(1) A = Active

3.7.2 Programs That Access This Table

Program Transaction Operation Details
DLISHIST DL06 OPEN/FETCH/CLOSE cursor Read all active incidents for the candidate; accumulate demerit points, check for active suspensions and unpaid fines

3.7.3 SQL Code Example — Driving History Cursor (DLISHIST)

COBOL 
EXEC SQL
    DECLARE HISTCUR CURSOR FOR
        SELECT INCIDENT_DATE, INCIDENT_TYPE, INCIDENT_DESC,
               DEMERIT_POINTS, FINE_AMOUNT, FINE_PAID_STATUS,
               SUSP_START_DATE, SUSP_END_DATE
        FROM   DLIS.DRIVING_HISTORY
        WHERE  CANDIDATE_ID  = :CANDIDATE-ID
        AND    RECORD_STATUS = 'A'
        ORDER BY INCIDENT_DATE DESC
END-EXEC

The history check fails if any of the following are true (evaluated in priority order):

  1. An active suspension or disqualification (INCIDENT_TYPE IN ('SU','DQ') with an open or future SUSP_END_DATE)
  2. Total DEMERIT_POINTS across all active incidents exceeds 12
  3. Any row has FINE_AMOUNT > 0 and FINE_PAID_STATUS = 'N'

6. DB2 Infrastructure

6.1 DB2 Bind and Plan Details

All DLIS programs share a single DB2 plan. The static SQL embedded in each program is precompiled using the DB2 precompiler (DSNHPC) and bound using JCL jcl/DLISBIND.jcl.

Attribute Value
DB2 Subsystem DSN1
Plan Name DLISPLAN
Collection DLISPKG
Bind JCL jcl/DLISBIND.jcl
Compile JCL jcl/DLISCOMP.jcl
Precompiler DSNHPC
Compiler IGYCRCTL

6.2 CICS-to-DB2 Connection

CICS accesses DB2 via a DB2ENTRY resource (DLISDB2E) defined in csd/DLISCSD.csd, bound to plan DLISPLAN. The entry supports a thread pool of up to 10 concurrent DB2 threads.

6.3 SQL Communication Area (SQLCA)

All programs include the standard DB2 SQL Communication Area via:

COBOL 
EXEC SQL INCLUDE SQLCA END-EXEC

The SQLCODE field is tested after every significant SQL operation. The standard codes used across all programs are:

SQLCODE Meaning How It Is Handled
0 Success Continue processing
+100 No row found Set “NOT FOUND” message, branch to exit paragraph
Any negative DB2 error Set generic database error message (for INSERT/UPDATE)

6.4 Host Variable Structures (DCLGEN)

All DB2 host variables are declared via DCLGEN-generated structures, consolidated in the shared copybook DLISDCLG (copybook/DLISDCLG.cpy):

Structure Name Maps To
DCLDLIS-CANDIDATE DLIS.CANDIDATE
DCLDLIS-LICENSE-APPL DLIS.LICENSE_APPLICATION
DCLDLIS-DRIVING-HIST DLIS.DRIVING_HISTORY
DCLDLIS-PAYMENT DLIS.PAYMENT
DCLDLIS-ISSUED-LIC DLIS.ISSUED_LICENSE
DCLDLIS-AUTH-USER DLIS.AUTHORITY_USER
DCLDLIS-FEE-SCHED DLIS.LICENSE_FEE_SCHEDULE

6.5 Schema DDL Artefacts

The DLIS DB2 schema is created and maintained via the following SQL and JCL artefacts:

File Purpose
db2/DLIS0001-CREATE-TABLES.sql Creates all seven DLIS tables
db2/DLIS0002-CREATE-INDEXES.sql Creates indexes (including unique index on CANDIDATE.ID_NUMBER)
db2/DLIS0003-GRANTS.sql Grants SELECT, INSERT, UPDATE, DELETE to the CICS execution user
jcl/DLISDB2.jcl JCL to run all three SQL scripts against subsystem DSN1
