Application Status Inquiry (DL04)

1. Overview

DLISSTAT is a CICS/COBOL online inquiry program in the Driver License Information System (DLIS). It runs as transaction DL04 and uses BMS mapset DLISST with map DLISST01. It is read-only. An operator enters an Application ID and the program shows how far that driver-license application has progressed through the licensing workflow.

For one application, the screen shows:

  • The license type, the two-character status code, and a readable status description.
  • The result, date, and notes or reference for each workflow stage:
    • Eligibility check
    • Driving-history check
    • Payment
    • First authority approval
    • Second authority approval
  • Once the license is issued, the license number, the expiry date, and an “issued” flag.

The operator presses ENTER to inquire and PF12 to exit.

1.1 Key Characteristics

Characteristic Description
Transaction ID DL04
Program DLISSTAT (Enterprise COBOL with embedded static Db2 SQL)
Screen Mapset DLISST, map DLISST01 (24×80 3270)
Interaction style Pseudo-conversational, with a 350-byte COMMAREA
Data access Two singleton SELECT statements, with no updates
Search key APPLICATION_ID
Other integration No MQ, VSAM, or QSAM

1.2 Place in the DLIS Landscape

DLISSTAT is the read-side counterpart to the DLIS programs that perform eligibility checking, history checking, payment, approval, and issuance. It changes none of the stages it reports. It shares the DLIS copybooks and the DLIS-COMMAREA navigation structure with those programs.

The terminal user starts transaction DL04, and CICS runs DLISSTAT. The program talks to the terminal through BMS map DLISST01 and keeps its session state in a 350-byte COMMAREA. It reaches Db2 through the CICS DB2ENTRY DLISDB2E, which binds the program to plan DLISPLAN on subsystem DSN1.

If the application has status IS but no matching ISSUED_LICENSE row is returned, the code does not set DST6FLGO. The license number and expiry fields stay unpopulated. The program still sets INQUIRY SUCCESSFUL in this case.

4.4 Execution Steps

  1. Entry. MAIN-LOGIC tests EIBCALEN. A value of 0 means first entry, so it performs INIT-SCREEN. Any other value means it restores the COMMAREA and performs PROCESS-INPUT.
  2. Initial screen. INIT-SCREEN moves the current date to DSTDATE, sends the blank map with ERASE (clear the screen) and FREEKB (unlock the keyboard), and returns with the transaction ID and COMMAREA.
  3. Receive and route. PROCESS-INPUT receives the map and evaluates EIBAID.
  4. Validate. INQUIRE-STATUS rejects a zero Application ID without touching Db2.
  5. Primary read. A singleton SELECT on DLIS.LICENSE_APPLICATION, keyed by APPLICATION_ID.
  6. Decode. The status code is translated to descriptive text.
  7. Populate. The five stage groups are moved to the map output fields.
  8. Conditional read. If the status is IS, a second SELECT reads DLIS.ISSUED_LICENSE.
  9. Complete. The message INQUIRY SUCCESSFUL is set, and the map is resent with DATAONLY. DATAONLY refreshes only the variable data, not the static labels.

7. Business Rules

7.1 Entry and Navigation

MAIN-LOGIC routes first-time and returning users:

COBOL 
IF EIBCALEN = 0
               PERFORM INIT-SCREEN
           ELSE
               MOVE DFHCOMMAREA TO DLIS-COMMAREA
               PERFORM PROCESS-INPUT
           END-IF

PROCESS-INPUT routes by attention key:

COBOL 
EVALUATE TRUE
               WHEN EIBAID = DFHENTER  PERFORM INQUIRE-STATUS
               WHEN EIBAID = DFHPF12   EXEC CICS RETURN END-EXEC
               OTHER
                   MOVE 'PRESS ENTER TO INQUIRE OR F12 TO EXIT'
                       TO DSTMSG
           END-EVALUATE

7.2 Application ID Validation

An Application ID is required before any lookup. This prevents a database call with empty search criteria.

COBOL 
IF DSTAIDI = ZEROS
               MOVE 'ENTER APPLICATION ID' TO DSTMSG
               GO TO INQUIRE-EXIT
           END-IF

7.3 Workflow Status Retrieval

The Application ID is the sole search key. One query returns all stage details.

COBOL

                      HIST_CHECK_NOTES,

                      APPROVAL_2_AUTHORITY

                      :ELIG-CHECK-STATUS, :ELIG-CHECK-DATE,
                      :ELIG-CHECK-NOTES,
                      :HIST-CHECK-STATUS, :HIST-CHECK-DATE,

7.6 Issued License Resolution

License details are shown only for issued applications. This prevents premature disclosure of license identifiers.

COBOL 
IF APPLICATION-STATUS OF DCLDLIS-LICENSE-APPL = 'IS'
               EXEC SQL
                   SELECT LICENSE_NUMBER, EXPIRY_DATE
                   INTO   :LICENSE-NUMBER, :EXPIRY-DATE
                          OF DCLDLIS-ISSUED-LIC
                   FROM   DLIS.ISSUED_LICENSE
                   WHERE  APPLICATION_ID = :APPLICATION-ID
                                           OF DCLDLIS-LICENSE-APPL
               END-EXEC
               IF SQLCODE = 0
                   MOVE LICENSE-NUMBER OF DCLDLIS-ISSUED-LIC TO DST6NUMO
                   MOVE EXPIRY-DATE    OF DCLDLIS-ISSUED-LIC TO DST6EXPO
                   MOVE 'YES'   TO DST6FLGO
               END-IF
           ELSE
               MOVE 'NO'  TO DST6FLGO
           END-IF

DST6FLGO is YES only when the status is IS and the issued-license row is found. It is NO when the status is not IS.

9. Error Handling

9.1 Handling Summary

Situation Handling User-visible result
Application ID is zero or blank GO TO INQUIRE-EXIT before any SQL ENTER APPLICATION ID
Unsupported attention key OTHER branch of EVALUATE PRESS ENTER TO INQUIRE OR F12 TO EXIT
Application not found (SQLCODE 100) Message set and exit APPLICATION NOT FOUND
Unrecognized status code OTHER branch of the status EVALUATE UNKNOWN STATUS in DSTADSO
Issued-license row missing or errored SQLCODE = 0 test fails, so the update is skipped silently License fields blank and flag not set
Other negative SQLCODE Not checked, so processing continues Possibly unreliable data shown
CICS response (WS-RESP1) Captured, never tested No visible effect

9.2 Observations and Risks

  • SQL error coverage. Only SQLCODE 100 (first query) and 0 (second query) are tested. Negative codes, such as a deadlock or an unavailable resource, fall through into normal display processing.
  • Unchecked CICS responses. WS-RESP1 is never inspected, so a MAPFAIL (for example, ENTER pressed with no data) is ignored. Because RESP is specified, the task does not abend.
  • Null indicators. WS-NULL-INDICATORS is defined but not used in the SELECT statements. A NULL in a nullable column such as ELIG_CHECK_DATE, APPROVAL_1_DATE, or EXPIRY_DATE would produce SQLCODE -305 in Db2. This program would not detect that.
  • Success message. INQUIRY SUCCESSFUL is also set when the issued-license query returns no row.
  • COMMAREA length. DFHCOMMAREA is 350 bytes and every RETURN uses LENGTH(350), but DLIS-COMMAREA is shorter. MOVE DFHCOMMAREA TO DLIS-COMMAREA truncates the extra bytes. A LENGTH larger than the data area is unpredictable and may cause LENGERR, so this should be reviewed.
  • STOP RUN. The program ends with STOP RUN, which is unusual in CICS. Every path issues EXEC CICS RETURN first.
  • Security. There is no user or authority check beyond CICS transaction-level security on DL04. Anyone who can run the transaction can inquire on any application ID.
  • Qualified host variables. The field OF structure form relies on the precompiler or coprocessor accepting it. Db2 documents the structure.field form.

10. Constraints

  • Input. The program does no numeric class, range, or length check on the ID beyond the zero test. APPLICATION-ID is PIC S9(10) COMP-3 and holds at most 10 digits.

  • Field sizes.

    Field Size
    License type 1 character
    Application status 2 characters
    Check and approval statuses 1 character each
    Payment reference 20 characters
    Notes 200 characters each
    Authority 50 characters each
    Date fields 10 characters each

  • Access mode. The program is read-only and issues only SELECT statements.

  • Row count. Each lookup is a singleton SELECT, so at most one row is processed. There is no cursor, and duplicate-key conditions are not handled.

  • Messages. All messages go through the single field DSTMSG. Only the last message assigned is shown.

  • Sequencing. The map is always received before EIBAID is evaluated, and INQUIRE-STATUS finishes before the DATAONLY send. PF12 ends the transaction before any further send occurs.

  • Pseudo-conversational. The program holds no resources between interactions.

Any other key, such as PF3 PRESS ENTER TO INQUIRE OR F12 TO EXIT EVALUATE falls to OTHER
PF12 Transaction ends and no map is resent RETURN without TRANSID
Status such as XX UNKNOWN STATUS in DSTADSO OTHER branch of the status EVALUATE

12.4 Example 4: First Invocation

The user types DL04, so EIBCALEN = 0. MAIN-LOGIC takes the INIT-SCREEN path and displays the blank DLISST01 screen with the current date in DSTDATE. The program then returns to DL04 with a 350-byte COMMAREA. Later invocations arrive with a non-zero EIBCALEN, copy DFHCOMMAREA into DLIS-COMMAREA, and run PROCESS-INPUT.

13. Modernization Notes

  • Service candidate. The logic suits a stateless “get application status” REST service. It takes an application ID, makes two keyed reads, and maps a status code to a description.
  • Status reference data. The PE → … → IS/RE mapping could move into shared reference data or an enumeration so all DLIS programs use one definition.
  • Session state. The pseudo-conversational COMMAREA corresponds to session or request context in a web or mobile front end.
  • Db2 access. The two reads could become a single join or a view over LICENSE_APPLICATION and ISSUED_LICENSE. That would reduce round trips and centralize null handling.
