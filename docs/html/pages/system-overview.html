DLIS System Overview

The Driver License Information System (DLIS) is an enterprise mainframe online transaction processing (OLTP) application designed for motor vehicle licensing authorities. Built on IBM z/OS utilizing IBM CICS (Customer Information Control System), COBOL for z/OS, and IBM Db2, DLIS manages the complete end-to-end lifecycle of driver licensing. The system enforces strict administrative business rules, multi-stage prerequisite validation gates, dual-authority approvals with segregation of duties, financial fee processing, and physical document issuance.

1. Overview

1.1 System Purpose and Business Scope

The primary objective of DLIS is to provide licensing clerks, inspecting officers, financial operators, and senior licensing authorities with an integrated, auditable, and secure online platform to process driver license candidates from initial registration through final license card generation.

DLIS addresses core operational requirements:

  • Candidate Registry Maintenance: Capture and maintenance of citizen demographic, identification, and residence data.
  • Application Ingestion & Tiered Pricing: Structured license application submission across Learner (L), Probationary (P), and Open/Full (O) license categories with dynamic fee calculation.
  • Automated Prerequisite Verification: Rigorous age verification, upgrade hierarchy validation (holding prerequisite license tiers), and detailed driving violation history assessment (checking demerit points, active suspensions/disqualifications, and outstanding fines).
  • Financial Settlement: Recording payments across diverse payment instruments and tying financial receipts to pending applications.
  • Dual-Level Administrative Governance: Multi-tier sign-off requiring independent Level 1 and Level 2 authority approvals with strict segregation of duties.
  • Document Production: Automated license number generation, expiry date calculation, and invocation of background printing routines.

1.2 End-to-End Licensing Process Lifecycle

The licensing lifecycle within DLIS follows a deterministic progression where each processing stage acts as an enforced operational gate for subsequent stages:

  1. Candidate Onboarding: The citizen is registered in the master candidate registry (DLISCAND), establishing a unique, system-generated Candidate ID.
  2. Application Submission: An application is created for a specific license class (DLISAPPL), capturing the requested tier (L, P, or O), checking active fee schedules, and initializing the application in Pending (PE) status.
  3. Gate 1 – Eligibility Verification: The candidate’s age and holding of predecessor licenses are evaluated (DLISELIG). A pass transitions the application to Eligibility Checked (EC).
  4. Gate 2 – Driving History Assessment: The candidate’s driving record is examined for demerit accumulations (> 12 points), active court disqualifications/suspensions, and unpaid fines (DLISHIST). A pass transitions the application to History Checked (HC).
  5. Gate 3 – Fee Collection: The applicant pays the statutory fee (DLISPAY). Payment settlement updates the application to Payment Approved (PA) and issues a formal receipt.
  6. Gate 4 – First-Level Authority Approval: A certified Level 1 authority officer inspects application artifacts and check notes, approving the record (DLISAP1) to advance it to Awaiting Second Approval (A2).
  7. Gate 5 – Second-Level Authority Approval: An independent Level 2 authority officer from a separate organizational unit performs final verification (DLISAP2), advancing the record to Fully Approved (AP).
  8. Final Issuance & Printing: An issuing officer assigns the vehicle class, registers statutory restrictions, and issues the license (DLISISSU). The application reaches Issued (IS) status, creating the master record in DLIS.ISSUED_LICENSE and linking to print modules (DLISLPRT).
  9. Continuous Inquiry: Clerks and applicants can track real-time stage-by-stage workflow milestones through transaction DL04 (DLISSTAT).

2.2 Pseudo-Conversational Execution Model & Session State

To maximize mainframe concurrency and minimize thread and memory occupancy, every DLIS program adheres strictly to the CICS pseudo-conversational programming model:

  1. Cold Start (EIBCALEN = 0): When a transaction is invoked initially, CICS provides an EIBCALEN of zero. The program formats the initial BMS map, issues EXEC CICS SEND MAP ... ERASE FREEKB, and immediately releases all task resources via EXEC CICS RETURN TRANSID('DLxx') COMMAREA(...) LENGTH(350).
  2. Terminal Wait State: No CICS task or active thread is held in memory while the user reads or enters data on the 3270 terminal.
  3. Conversational Re-entry (EIBCALEN > 0): When the operator presses an Attention Identifier (AID) key (e.g., Enter, PF1, PF3, PF12), CICS initiates a new task, copies the persisted 350-byte DFHCOMMAREA into the program’s Linkage Section, receives the modified map fields (EXEC CICS RECEIVE MAP), executes the requested business logic, re-sends the screen with DATAONLY, and re-arms the transaction loop.
  4. Session Termination: Pressing PF12 triggers an unconditional EXEC CICS RETURN without specifying a TRANSID, cleanly ending the user session.

4. Subsystem Transactions & Program Specifications

4.1 Navigation Hub: DLISMENU (DL01)

DLISMENU provides the primary entry point for terminal operators. It renders a clean selection menu (BMS Map DLISMM01) displaying options 1 through 10.

  • Routing Engine: Maps operator input options to target downstream transaction programs.
  • Session Context Passing: Preserves user identity, message areas, and entity IDs across pseudo-conversational cycles and transfers control using EXEC CICS XCTL.

4.2 Candidate Management: DLISCAND (DL02)

DLISCAND is the master candidate demographic maintenance module.

  • Actions Driven by Function Keys:
    • F1 (Create): Validates that First Name, Last Name, and National ID are present; performs duplicate detection on active records (RECORD_STATUS = 'A'); inserts into DLIS.CANDIDATE; retrieves the auto-generated identity ID via IDENTITY_VAL_LOCAL().
    • F2 (Update): Updates candidate demographic, address, telephone, and email details for a given Candidate ID.
    • F3 (Inquire): Retrieves candidate information by Candidate ID or National ID number (FETCH FIRST 1 ROW ONLY).
    • F4 (Deactivate): Executes a logical soft-delete by updating RECORD_STATUS = 'I'.

4.3 Application Entry & Fee Lookup: DLISAPPL (DL03)

DLISAPPL handles license application intake.

  • Candidate Verification (F3): Validates that the Candidate ID exists and is active (RECORD_STATUS <> 'I').
  • Dynamic Fee Calculation (F5): Queries DLIS.LICENSE_FEE_SCHEDULE for Initial Fees (FEE_TYPE = 'IF') where ACTIVE_STATUS = 'A' and current date falls between EFFECTIVE_DATE and EXPIRY_DATE.
  • Application Submission (F1): Validates license category domain (L for Learner, P for Probation, O for Open); verifies that no duplicate active application exists for that candidate and license category (excluding terminal statuses RE and IS); inserts the record into DLIS.LICENSE_APPLICATION in Pending (PE) status.

4.4 Status Tracking & Inquiries: DLISSTAT (DL04)

DLISSTAT provides end-to-end visibility into any license application in flight.

  • Multi-Stage Reporting: Inquires by APPLICATION_ID and renders the real-time status of all 5 processing gates:
    1. Eligibility Check (Status, Date, Notes)
    2. History Check (Status, Date, Notes)
    3. Payment Settlement (Status, Reference)
    4. Authority 1 Approval (Status, Date, Reviewer)
    5. Authority 2 Approval (Status, Date, Reviewer)
  • Conditional License Inspection: If APPLICATION_STATUS = 'IS', the program issues a secondary query against DLIS.ISSUED_LICENSE to display the active License Number and Expiry Date.

4.5 Eligibility Verification Gate: DLISELIG (DL05)

DLISELIG implements the first business gate.

  • Age Rules: Computes age as CURRENT_YEAR - DOB_YEAR and enforces statutory minimums:
    • Learner (L): Minimum age 16
    • Probationary (P): Minimum age 17
    • Open (O): Minimum age 18
  • Upgrade Hierarchy Rules:
    • Applicants for Probation (P) must hold an active Learner (L) license (DLIS.ISSUED_LICENSE count > 0).
    • Applicants for Open (O) must hold an active Probationary (P) license.
  • Persistence: Updates ELIG_CHECK_STATUS (P/F), ELIG_CHECK_NOTES, and advances APPLICATION_STATUS to EC (or RE on failure).

4.6 Driving History Assessment Gate: DLISHIST (DL06)

DLISHIST implements the second business gate via cursor-driven violation assessment.

  • Prerequisite Gate: Re-verifies that ELIG_CHECK_STATUS = 'P'; otherwise rejects processing with "ELIGIBILITY CHECK MUST BE PASSED FIRST".
  • Cursor Scanning (HISTCUR): Scans all active driving history incidents (RECORD_STATUS = 'A') for the candidate:
    • Suspension / Disqualification: Checks for incident types SU or DQ with open-ended or future expiry dates (SUSP_END_DATE >= CURRENT DATE).
    • Demerit Accumulation: Sums all incident demerit points; fails if cumulative WS-DEMERIT-TOTAL > 12.
    • Unpaid Fines: Fails if any incident contains FINE_AMOUNT > 0 and FINE_PAID_STATUS = 'N'.
  • Screen Grid: Renders a scrollable 7-row incident display window (navigated using F7/F8).
  • Persistence: Updates HIST_CHECK_STATUS (P/F), records failure notes, and sets APPLICATION_STATUS to HC (or RE).

4.7 Fee Collection & Receipting: DLISPAY (DL07)

DLISPAY governs financial fee processing.

  • Prerequisite Gate: Enforces that HIST_CHECK_STATUS = 'P' and guards against duplicate payment (PAYMENT_STATUS <> 'P').
  • Payment Method Validation: Validates payment method against allowed codes: Credit Card (CC), Debit Card (DC), EFTPOS (EF), Cash (CS), or Cheque (CH).
  • Receipt Construction: Formats receipt number as RCP + YYYYMMDD + APPLICATION_ID.
  • Persistence & Inter-Module Link: Inserts payment record into DLIS.PAYMENT, updates LICENSE_APPLICATION to status PA and PAYMENT_STATUS = 'P'. Function key F5 triggers EXEC CICS LINK PROGRAM('DLISRPRT') to print formal customer receipts.

4.8 Dual-Authority Approval Gates: DLISAP1 (DL08) & DLISAP2 (DL09)

Administrative sign-off requires two independent approving authorities:

  • First Authority (DLISAP1 / DL08):
    • Requires PAYMENT_STATUS = 'P'.
    • Validates officer in DLIS.AUTHORITY_USER (ACTIVE_STATUS = 'A', AUTHORITY_LEVEL = '1').
    • Verifies officer is authorized for the application’s license type (LIC_TYPES_AUTH).
    • Updates APPROVAL_1_STATUS, APPROVAL_1_AUTHORITY, and sets APPLICATION_STATUS to A2 (Approved) or RE (Rejected).
  • Second Authority (DLISAP2 / DL09):
    • Requires APPROVAL_1_STATUS = 'A'.
    • Validates officer in DLIS.AUTHORITY_USER (ACTIVE_STATUS = 'A', AUTHORITY_LEVEL = '2').
    • Segregation of Duties Enforcement: Compares AUTHORITY-NAME of Approver 2 against APPROVAL_1_AUTHORITY; rejects if identical with "SECOND APPROVER MUST BE FROM DIFFERENT AUTHORITY".
    • Updates APPROVAL_2_STATUS and transitions APPLICATION_STATUS to AP (Fully Approved) or RE.

4.9 Final License Issuance & Printing: DLISISSU (DL10)

DLISISSU performs final document generation.

  • Prerequisite Gate: Verifies that APPLICATION_STATUS = 'AP'.
  • Validation: Enforces valid vehicle class (A, B, C, or D), non-blank issuing officer, and issuing authority.
  • Expiry & Identifier Computation:
    • Learner (L): Validity 1 Year, Prefix LRN
    • Probationary (P): Validity 2 Years, Prefix PRB
    • Open (O): Validity 5 Years, Prefix OPN
    • LICENSE_NUMBER: Built from PREFIX + VEHICLE_CLASS + CANDIDATE_ID + APPLICATION_ID.
  • Persistence & Printing: Inserts master record into DLIS.ISSUED_LICENSE with initial demerit balance of 12; updates LICENSE_APPLICATION to IS (Issued); provides F6 shortcut to invoke printing via EXEC CICS LINK PROGRAM('DLISLPRT').

5.2 Core Database Tables and Persistence Rules

  • Referential Integrity: All transactional records (LICENSE_APPLICATION, DRIVING_HISTORY, PAYMENT, ISSUED_LICENSE) are explicitly bound to master CANDIDATE and LICENSE_APPLICATION records.
  • Audit Traceability: Every table update captures LAST_UPDATED_DATE = CURRENT DATE and records the acting terminal ID (EIBTRMID) or authenticated officer code (USER_CODE).
  • Soft Deletion: Citizen and history deactivations utilize status flags (RECORD_STATUS = 'I') rather than physical record purging to maintain historical auditability.

6. Technical Implementation Patterns & Code Examples

6.1 Pseudo-Conversational Flow Control Pattern

Every online module implements the standardized CICS pseudo-conversational dispatcher shown below (excerpted from DLISELIG.cbl / DLISAP1.cbl):

COBOL 
MAIN-LOGIC.
           MOVE EIBTRNID TO CA-TRANSACTION-ID OF DLIS-COMMAREA
           IF EIBCALEN = 0
               PERFORM INIT-SCREEN
           ELSE
               MOVE DFHCOMMAREA TO DLIS-COMMAREA
               PERFORM PROCESS-INPUT
           END-IF
           STOP RUN.

       INIT-SCREEN.
           MOVE CURRENT-DATE(1:10) TO DECDATE OF DLISEC01O
           EXEC CICS SEND
               MAP('DLISEC01')
               MAPSET('DLISEC')
               ERASE
               FREEKB
               RESP(WS-RESP1)
           END-EXEC
           EXEC CICS RETURN
               TRANSID('DL05')
               COMMAREA(DLIS-COMMAREA)
               LENGTH(350)
           END-EXEC.

       PROCESS-INPUT.
           EXEC CICS RECEIVE
               MAP('DLISEC01')
               MAPSET('DLISEC')
               RESP(WS-RESP1)
           END-EXEC
           
           EVALUATE TRUE
               WHEN EIBAID = DFHPF1
                   PERFORM RUN-ELIGIBILITY-CHECK
               WHEN EIBAID = DFHPF3
                   PERFORM LOAD-APPLICATION
               WHEN EIBAID = DFHPF12
                   EXEC CICS RETURN END-EXEC
               WHEN OTHER
                   MOVE 'USE F1 F3 OR F12' TO DECMSG OF DLISEC01O
           END-EVALUATE

           EXEC CICS SEND
               MAP('DLISEC01')
               MAPSET('DLISEC')
               DATAONLY
               FREEKB
               RESP(WS-RESP1)
           END-EXEC
           EXEC CICS RETURN
               TRANSID('DL05')
               COMMAREA(DLIS-COMMAREA)
               LENGTH(350)
           END-EXEC.

6.2 Shared Communication Area Structure (DLIS-COMMAREA)

The application standardizes inter-program context sharing using DLISCSEC.cpy. When passing state across pseudo-conversational invocations, programs preserve candidate, application, and user contexts:

COBOL 
* Moving screen context into COMMAREA before next turn
           MOVE DSTAIDI  TO CA-APPLICATION-ID OF DLIS-COMMAREA
           MOVE EIBTRNID TO CA-TRANSACTION-ID OF DLIS-COMMAREA
           MOVE EIBTRMID TO CA-USER-ID        OF DLIS-COMMAREA

6.3 Program Transfer and Dynamic Routing (EXEC CICS XCTL / LINK)

Dynamic subsystem invocation occurs either through full control transfer (XCTL) from the menu hub or modular synchronous execution (LINK) for physical receipt and license printing:

COBOL 
* Invoking receipt printing utility synchronously (from DLISPAY)
       PRINT-RECEIPT.
           IF DPERCTO OF DLISPE01O = SPACES
               MOVE 'PROCESS PAYMENT FIRST BEFORE PRINTING'
                 TO DPEMSG OF DLISPE01O
               GO TO PRINT-RECEIPT-EXIT
           END-IF

           EXEC CICS LINK
               PROGRAM('DLISRPRT')
               COMMAREA(DLIS-COMMAREA)
               LENGTH(350)
           END-EXEC

           MOVE 'RECEIPT SENT TO PRINTER' TO DPEMSG OF DLISPE01O.
       PRINT-RECEIPT-EXIT.
           EXIT.

6.4 Relational Persistence & Atomic Status Transitions (Embedded SQL)

Status advancement occurs via embedded SQL statements with atomic field updates and audit tracking. The example below shows the Segregation of Duties and Second Approval update from DLISAP2:

COBOL 
* Segregation of Duties Check and Status Update in DLISAP2
           IF AUTHORITY-NAME OF DCLDLIS-AUTH-USER = WS-APPROVAL1-AUTH
               MOVE 'SECOND APPROVER MUST BE FROM DIFFERENT AUTHORITY'
                 TO DA2MSG OF DLISA2M01O
               GO TO SUBMIT-A2-EXIT
           END-IF

           IF DA2DECI OF DLISA2M01I = 'A'
               MOVE 'AP' TO APPLICATION-STATUS OF DCLDLIS-LICENSE-APPL
           ELSE
               MOVE 'RE' TO APPLICATION-STATUS OF DCLDLIS-LICENSE-APPL
           END-IF

           EXEC SQL
               UPDATE DLIS.LICENSE_APPLICATION
               SET    APPROVAL_2_STATUS    = :WS-DECISION,
                      APPROVAL_2_AUTHORITY = :AUTHORITY-NAME,
                      APPROVAL_2_DATE      = CURRENT DATE,
                      APPROVAL_2_NOTES      = :DA2DCNTI,
                      APPLICATION_STATUS   = :APPLICATION-STATUS,
                      LAST_UPDATED_DATE    = CURRENT DATE,
                      LAST_UPDATED_BY      = :DA2AUCOI
               WHERE  APPLICATION_ID       = :APPLICATION-ID
           END-EXEC.
