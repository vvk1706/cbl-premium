License Application Entry (DL03)

1. Overview

DLISAPPL is a CICS pseudo-conversational COBOL program that drives transaction DL03 — the License Application Entry screen in a driver licensing information system. It provides licensing office clerks with a structured, interactive screen to:

  • Look up a candidate by ID to verify identity and active standing (F3)
  • Retrieve the current initial-issue fee for a chosen license type — Learner (L), Probation (P), or Open (O) — from the active fee schedule (F5)
  • Submit a new pending license application for a verified candidate (F1), with automatic duplicate open-application detection

The program uses BMS map DLISAE01 (mapset DLISAE) for all screen I/O and interfaces with three IBM Db2 tables in the DLIS schema. It is the sole entry point for new license applications in the system; every downstream workflow step — eligibility checking, driving-history review, payment processing, dual approvals, and license issuance — depends on the application record this program creates.

Each user interaction is a discrete CICS task. State is preserved across key presses via a 350-byte COMMAREA passed through EXEC CICS RETURN TRANSID('DL03'). Pressing F12 ends the conversation cleanly.

2. System Architecture

DLISAPPL sits at the intersection of the CICS terminal layer, BMS screen management, and the Db2 database back end. The diagram below shows the principal components and their relationships.

The clerk interacts exclusively through the BMS map. DLISAPPL receives each key press, applies business rules, performs the necessary Db2 operations, and refreshes the screen with results or error messages — all within a single, short-lived CICS task.

3. Processing Logic

3.1 High-Level Execution Flow

3.2 Candidate Lookup — F3 (LOOKUP-CANDIDATE)

Pressing F3 triggers a database lookup on DLIS.CANDIDATE. The sequence below shows the exact interactions between the clerk, the program, and Db2.

sequenceDiagram actor Clerk participant PGM as DLISAPPL participant DB2 as DLIS.CANDIDATE Clerk->>PGM: Press F3 with Candidate ID PGM->>PGM: Check DAECIDI ≠ ZEROS alt Candidate ID is zero PGM-->>Clerk: DAEMSG = 'ENTER CANDIDATE ID' else Candidate ID provided PGM->>DB2: SELECT FIRST_NAME, LAST_NAME, RECORD_STATUS\nWHERE CANDIDATE_ID = :CANDIDATE-ID DB2-->>PGM: Row / SQLCODE 100 / error alt SQLCODE = 100 — not found PGM-->>Clerk: DAEMSG = 'CANDIDATE NOT FOUND' else RECORD_STATUS = 'I' — inactive PGM-->>Clerk: DAEMSG = 'CANDIDATE RECORD IS INACTIVE' else Active candidate found PGM->>PGM: STRING FIRST-NAME ' ' LAST-NAME → DAECNAMO PGM-->>Clerk: DAECNAMO = full name\nDAEMSG = 'CANDIDATE FOUND' end end

Key code — candidate name formatting:

COBOL 
STRING FIRST-NAME OF DCLDLIS-CANDIDATE DELIMITED SPACE
                  ' '        DELIMITED SIZE
                  LAST-NAME  OF DCLDLIS-CANDIDATE DELIMITED SPACE
               INTO DAECNAMO
           MOVE 'CANDIDATE FOUND' TO DAEMSG.

Key code — existence and status checks:

COBOL 
IF DAECIDI = ZEROS
               MOVE 'ENTER CANDIDATE ID' TO DAEMSG
               GO TO LOOKUP-CANDIDATE-EXIT
           END-IF

           IF SQLCODE = 100
               MOVE 'CANDIDATE NOT FOUND' TO DAEMSG
               GO TO LOOKUP-CANDIDATE-EXIT
           END-IF

           IF RECORD-STATUS OF DCLDLIS-CANDIDATE = 'I'
               MOVE 'CANDIDATE RECORD IS INACTIVE' TO DAEMSG
               GO TO LOOKUP-CANDIDATE-EXIT
           END-IF

Note: Only SQLCODE = 100 is explicitly handled. Other negative SQLCODEs (e.g., deadlock, authority errors) are not intercepted and the program will continue with undefined host-variable content.

3.3 Fee Calculation — F5 (CALC-FEE)

Pressing F5 retrieves the current initial-issue fee (FEE_TYPE = 'IF') for the selected license type from the active, date-effective fee schedule.

sequenceDiagram actor Clerk participant PGM as DLISAPPL participant DB2 as DLIS.LICENSE_FEE_SCHEDULE Clerk->>PGM: Press F5 with License Type (L / P / O) PGM->>PGM: Check DAELTYPI ≠ SPACES or LOW-VALUES alt License type blank PGM-->>Clerk: DAEMSG = 'SELECT LICENSE TYPE FIRST' else License type entered PGM->>DB2: SELECT FEE_AMOUNT, CURRENCY_CODE\nWHERE LICENSE_TYPE = :type\nAND FEE_TYPE = 'IF'\nAND ACTIVE_STATUS = 'A'\nAND EFFECTIVE_DATE <= CURRENT DATE\nAND (EXPIRY_DATE IS NULL OR EXPIRY_DATE >= CURRENT DATE)\nFETCH FIRST 1 ROW ONLY DB2-->>PGM: Row / SQLCODE 100 alt SQLCODE = 100 — no schedule PGM-->>Clerk: DAEMSG = 'NO FEE SCHEDULE FOR THIS LICENSE TYPE' else Fee schedule found PGM->>PGM: Format FEE-AMOUNT → WS-FEE-AMOUNT-D (ZZZ,ZZ9.99) PGM-->>Clerk: DAEFEEO = formatted amount\nDAECURRO = currency code\nDAEMSG = 'FEE RETRIEVED SUCCESSFULLY' end end

Key code — fee retrieval SQL:

COBOL 
MOVE DAELTYPI TO LICENSE-TYPE OF DCLDLIS-FEE-SCHED
           EXEC SQL
               SELECT FEE_AMOUNT, CURRENCY_CODE
               INTO   :FEE-AMOUNT, :CURRENCY-CODE
               OF DCLDLIS-FEE-SCHED
               FROM   DLIS.LICENSE_FEE_SCHEDULE
               WHERE  LICENSE_TYPE  = :LICENSE-TYPE OF DCLDLIS-FEE-SCHED
               AND    FEE_TYPE      = 'IF'
               AND    ACTIVE_STATUS = 'A'
               AND    EFFECTIVE_DATE <= CURRENT DATE
               AND    (EXPIRY_DATE IS NULL OR EXPIRY_DATE >= CURRENT DATE)
               FETCH FIRST 1 ROW ONLY
           END-EXEC

Key code — fee formatting:

COBOL 
MOVE FEE-AMOUNT    OF DCLDLIS-FEE-SCHED TO WS-FEE-AMOUNT
           MOVE WS-FEE-AMOUNT TO WS-FEE-AMOUNT-D
           MOVE WS-FEE-AMOUNT-D TO DAEFEEO
           MOVE CURRENCY-CODE OF DCLDLIS-FEE-SCHED TO DAECURRO
           MOVE 'FEE RETRIEVED SUCCESSFULLY' TO DAEMSG.

WS-FEE-AMOUNT-D has picture ZZZ,ZZ9.99, accommodating fees up to 999,999.99. Fees of 1,000,000 or more would be silently truncated on display.

3.4 Application Submission — F1 (SUBMIT-APPLICATION)

Pressing F1 is the core transactional operation. It runs three ordered validations, a duplicate-application check, a Db2 INSERT, and finally retrieves the system-generated application ID.

Key code — input validations:

COBOL 
IF DAECIDI = ZEROS
               MOVE 'CANDIDATE ID IS REQUIRED' TO DAEMSG
               GO TO SUBMIT-APPLICATION-EXIT
           END-IF
           IF DAELTYPI = SPACES OR DAELTYPI = LOW-VALUES
               MOVE 'LICENSE TYPE IS REQUIRED' TO DAEMSG
               GO TO SUBMIT-APPLICATION-EXIT
           END-IF
           IF DAELTYPI NOT = 'L' AND DAELTYPI NOT = 'P'
                               AND DAELTYPI NOT = 'O'
               MOVE 'LICENSE TYPE MUST BE L P OR O' TO DAEMSG
               GO TO SUBMIT-APPLICATION-EXIT
           END-IF

Key code — duplicate application check:

COBOL 
MOVE DAECIDI  TO CANDIDATE-ID  OF DCLDLIS-LICENSE-APPL
           MOVE DAELTYPI TO LICENSE-TYPE  OF DCLDLIS-LICENSE-APPL
           EXEC SQL
               SELECT COUNT(*) INTO :APPLICATION-ID OF DCLDLIS-LICENSE-APPL
               FROM   DLIS.LICENSE_APPLICATION
               WHERE  CANDIDATE_ID   = :CANDIDATE-ID   OF DCLDLIS-LICENSE-APPL
               AND    LICENSE_TYPE   = :LICENSE-TYPE   OF DCLDLIS-LICENSE-APPL
               AND    APPLICATION_STATUS NOT IN ('RE','IS')
           END-EXEC
           IF APPLICATION-ID OF DCLDLIS-LICENSE-APPL > 0
               MOVE 'ACTIVE APPLICATION ALREADY EXISTS FOR THIS TYPE'
                   TO DAEMSG
               GO TO SUBMIT-APPLICATION-EXIT
           END-IF

Key code — application insert and identity retrieval:

COBOL 
MOVE EIBTRMID TO CREATED-BY OF DCLDLIS-LICENSE-APPL
           EXEC SQL
               INSERT INTO DLIS.LICENSE_APPLICATION
                  (CANDIDATE_ID, LICENSE_TYPE, APPLICATION_STATUS,
                   CREATED_BY, LAST_UPDATED_BY)
               VALUES
                  (:CANDIDATE-ID, :LICENSE-TYPE, 'PE',
                   :CREATED-BY, :CREATED-BY)
               OF DCLDLIS-LICENSE-APPL
           END-EXEC

           EXEC SQL
               SELECT IDENTITY_VAL_LOCAL()
               INTO   :APPLICATION-ID OF DCLDLIS-LICENSE-APPL
               FROM   SYSIBM.SYSDUMMY1
           END-EXEC

           MOVE APPLICATION-ID OF DCLDLIS-LICENSE-APPL TO DAEAIDO
           MOVE 'PE'           TO DAEASTTO
           MOVE CURRENT-DATE(1:10) TO DAEADATO
           MOVE 'APPLICATION SUBMITTED SUCCESSFULLY' TO DAEMSG.

Key code — function key dispatch (PROCESS-INPUT):

COBOL 
EVALUATE TRUE
               WHEN EIBAID = DFHPF1   PERFORM SUBMIT-APPLICATION
               WHEN EIBAID = DFHPF3   PERFORM LOOKUP-CANDIDATE
               WHEN EIBAID = DFHPF5   PERFORM CALC-FEE
               WHEN EIBAID = DFHPF12  EXEC CICS RETURN END-EXEC
               OTHER
                   MOVE 'USE F1 F3 F5 OR F12' TO DAEMSG
           END-EVALUATE

7. Business Rules

7.1 Candidate Eligibility

  • A candidate ID of zero is always rejected before any database access.
  • Only candidates with an existing row in DLIS.CANDIDATE are accepted.
  • Candidates with RECORD_STATUS = 'I' (inactive) are blocked from any further processing.

7.2 License Type Domain

  • Valid license types for new applications are L (Learner), P (Probation), and O (Open) only.
  • This rule is enforced independently in both the fee calculation and the submission paths.

7.3 Fee Schedule Selection

  • Only fee rows with FEE_TYPE = 'IF' (initial fee) and ACTIVE_STATUS = 'A' qualify.
  • The row must be currently effective: EFFECTIVE_DATE <= CURRENT DATE and EXPIRY_DATE IS NULL OR EXPIRY_DATE >= CURRENT DATE.
  • FETCH FIRST 1 ROW ONLY ensures a single result when multiple qualifying rows exist.

7.4 Duplicate Application Prevention

  • A candidate may hold at most one active application per license type at any given time.
  • Applications with status RE (rejected) or IS (issued) are excluded from the active count — they are considered terminal states.
  • Any other status (e.g., PE — pending) counts as active and blocks a new submission.

7.5 Initial Application State

  • Every new application is created with status PE (Pending) — this is hard-coded.
  • The submitting terminal ID (EIBTRMID) is recorded in both CREATED_BY and LAST_UPDATED_BY for audit purposes.
  • The application ID is system-generated by Db2 (identity column) and retrieved via IDENTITY_VAL_LOCAL().

7.6 Commit Behaviour

  • There is no explicit SYNCPOINT. The INSERT is committed implicitly when the CICS task ends via EXEC CICS RETURN. A failed insert is not explicitly rolled back; recovery depends on the CICS task-end default.

All errors follow a consistent pattern: set DAEMSG, branch to the paragraph’s exit label via GO TO, refresh the screen with DATAONLY, and return the transaction for another cycle. Only the first failing rule in each paragraph is reported per interaction.

8.2 Known Gaps in Error Coverage

Area Gap
Candidate SELECT Only SQLCODE = 100 is handled; other negative SQLCODEs (deadlock, authority) are silently ignored

Duplicate-count SELECT SQLCODE is not checked at all; a failed query leaves the count unreliable
IDENTITY_VAL_LOCAL() retrieval SQLCODE is not checked; a failure could display a wrong ID with a success message

10. Constraints and Limitations

10.1 Pseudo-Conversational Design

  • DFHCOMMAREA is fixed at PIC X(350). No state exceeding 350 bytes can be carried between interactions.
  • The COMMAREA is moved from DFHCOMMAREA without a length check; the program assumes a compatible layout from the caller.

10.2 Candidate Name Formatting

  • STRING ... DELIMITED SPACE truncates each name component at its first embedded space. Multi-word first or last names are cut short.
  • There is no ON OVERFLOW clause on the STRING statement; overflow is silently truncated.

10.3 Fee Display

  • WS-FEE-AMOUNT-D (ZZZ,ZZ9.99) supports at most six integer digits. Fees ≥ 1,000,000 are silently truncated.

10.4 Duplicate Check Race Condition

  • The duplicate-count SELECT and the INSERT are two separate statements with no intervening lock. Two concurrent F1 presses for the same candidate and type could both pass the count check before either insert completes.

10.5 Submit Does Not Re-verify Candidate

  • SUBMIT-APPLICATION does not check that the candidate exists or is active. That check is only performed during the F3 lookup. A clerk can submit an application without having first performed a lookup; integrity is then enforced only by database referential constraints.

10.6 No Logging

  • The program writes no error logs, no CICS temporary storage entries, and no console messages. SQLCODE and CICS response values are not recorded for diagnostics.
