Second-Level Authority Approval (DL09)

1. Overview

DLISAP2 is a CICS COBOL program that runs as transaction DL09. It handles the second-level authority approval step of a driver’s licence application workflow. An authorised reviewer uses a BMS screen (map DLISA2M01, mapset DLISA2) to do the following:

  • Load an application by its ID. The screen shows the candidate’s name, licence type, eligibility, history and payment status, and the first approver’s details.
  • Identify themselves with an authority user code. The program checks that code against the database.
  • Submit an Approve (A) or Reject (R) decision.

Before it accepts a decision, the program enforces these controls:

Control Description
First-approval prerequisite APPROVAL_1_STATUS must be A.
Active level-2 approver The user must be active (ACTIVE_STATUS = 'A') and at AUTHORITY_LEVEL = '2'.
Segregation of duties The second approver’s authority must differ from the first approver’s authority.
Licence-type authorisation The application’s licence type must be in the approver’s authorised list (LIC_TYPES_AUTH).

If every check passes, the program updates LICENSE_APPLICATION. It records the second approval status, authority, date, notes and audit user. It also sets the overall status:

  • AP: approved, ready for licence issuance.
  • RE: rejected, application closed.

1.1 Function Keys

Key Action Paragraph
F1 Submit the second approval decision SUBMIT-APPROVAL2
F3 Load the application LOAD-APPLICATION
F4 Validate the authority user VALIDATE-AUTHORITY
F12 Exit the transaction (EXEC CICS RETURN)
Other Show “USE F1 F3 F4 OR F12” PROCESS-INPUT

AUTHORITY_USER has no foreign key to the other tables. It is linked logically at run time: the user’s AUTHORITY_NAME is compared with APPROVAL_1_AUTHORITY, and the application’s LICENSE_TYPE is checked against LIC_TYPES_AUTH.

3. Inputs and Outputs

3.1 Inputs

3.1.1 COMMAREA

DFHCOMMAREA is 350 bytes and is overlaid onto DLIS-COMMAREA on every re-entry. It holds:

  • CA-TRANSACTION-ID (DL09)
  • CA-RETURN-SCREEN
  • CA-APPLICATION-ID
  • CA-USER-ID

3.1.2 BMS Screen Fields

Field Description
DA2AIDI Application ID typed by the operator.
DA2AUCOI Authority user code. Also written to LAST_UPDATED_BY.
DA2DECI Decision: A = approve, R = reject.
DA2DCNTI Decision notes, stored as APPROVAL_2_NOTES.
EIBAID Attention identifier (PF1, PF3, PF4, PF12).

3.1.3 DB2 Tables Read

Table Columns used Purpose
DLIS.LICENSE_APPLICATION LICENSE_TYPE, APPLICATION_STATUS, ELIG_CHECK_STATUS, HIST_CHECK_STATUS, PAYMENT_STATUS, APPROVAL_1_STATUS, APPROVAL_1_AUTHORITY Display and gate checks.
DLIS.CANDIDATE FIRST_NAME, LAST_NAME Candidate full name.
DLIS.AUTHORITY_USER USER_NAME, AUTHORITY_NAME, AUTHORITY_LEVEL, LIC_TYPES_AUTH Approver validation, segregation and licence-type checks.

3.2 Outputs

3.2.1 Screen Output Fields

Field Content
DA2MSG Message for every interaction: errors, progress and the final outcome.
DA2CNAMO Candidate full name (first name + space + last name).
DA2LTYO Licence type.
DA2ELIGO, DA2HISTO, DA2PAYO Eligibility, history and payment statuses.
DA2A1STO, DA2A1NMO First approval status and authority name.
DA2AUNMO Validated authority name of the second approver.
DA2DATE Current date on the initial screen.

The UPDATE on DLIS.LICENSE_APPLICATION sets:

Column Source

APPROVAL_2_AUTHORITY AUTHORITY-NAME of the validated approver

APPLICATION_STATUS 'AP' or 'RE'
LAST_UPDATED_DATE CURRENT DATE

4.3 Entry and Screen Handling

4.3.1 MAIN-LOGIC

  • If EIBCALEN = 0, this is the first invocation and the program performs INIT-SCREEN.
  • Otherwise it copies DFHCOMMAREA into DLIS-COMMAREA and performs PROCESS-INPUT.
  • It then reaches STOP RUN.

4.3.2 INIT-SCREEN

  • Moves the first 10 characters of CURRENT-DATE to DA2DATE.
  • Sends the map with ERASE and FREEKB.
  • Issues EXEC CICS RETURN TRANSID('DL09') with the 350-byte COMMAREA.

4.3.3 PROCESS-INPUT

  • Receives the map and dispatches on EIBAID with EVALUATE TRUE.
  • After the chosen action, it re-sends the map with DATAONLY and FREEKB.
  • It then returns with TRANSID('DL09') and the COMMAREA.
  • F12 issues EXEC CICS RETURN with no TRANSID, which ends the conversation.

4.4 Load Application (F3)

graph TD J[LOAD-APPLICATION] --> J1{Application ID entered} J1 -- No --> J2[Message: ENTER APPLICATION ID] J1 -- Yes --> J3[SELECT application JOIN candidate] J3 --> J4{SQLCODE = 100} J4 -- Yes --> J5[Message: APPLICATION NOT FOUND] J4 -- No --> J6[Show name, licence type, check statuses,
first approval details] J6 --> J7[Save WS-APPROVAL1-AUTH
Message: APPLICATION LOADED]

The program joins the two tables on CANDIDATE_ID. It builds the full name with STRING and saves the first approver’s authority in WS-APPROVAL1-AUTH for the later segregation check.

4.5 Validate Authority (F4)

graph TD K[VALIDATE-AUTHORITY] --> K1{User code entered} K1 -- No --> K2[Message: ENTER AUTHORITY USER CODE] K1 -- Yes --> K3[SELECT active level-2 user] K3 --> K4{SQLCODE = 100} K4 -- Yes --> K5[Message: NOT FOUND OR NOT ACTIVE AT LEVEL 2] K4 -- No --> K6[Show authority name
Message: AUTHORITY USER VALIDATED]

The SQL statement filters on the user’s activity and level:

COBOL 
EXEC SQL
               SELECT USER_NAME, AUTHORITY_NAME, AUTHORITY_LEVEL,
                      LIC_TYPES_AUTH
               INTO   :USER-NAME, :AUTHORITY-NAME, :AUTHORITY-LEVEL,
                      :LIC-TYPES-AUTH OF DCLDLIS-AUTH-USER
               FROM   DLIS.AUTHORITY_USER
               WHERE  USER_CODE       = :USER-CODE OF DCLDLIS-AUTH-USER
               AND    ACTIVE_STATUS   = 'A'
               AND    AUTHORITY_LEVEL = '2'
           END-EXEC
           IF SQLCODE = 100
               MOVE 'AUTHORITY USER NOT FOUND OR NOT ACTIVE AT LEVEL 2'
                   TO DA2MSG
               GO TO VALIDATE-AUTH-EXIT
           END-IF

Inactive users and users at the wrong level have no separate error branch. The WHERE clause excludes them, and they surface as SQLCODE = 100.

4.6 Submit Second Approval (F1)

The submit paragraph runs its checks in a fixed order. The first failure puts a message on the screen and exits without updating.

graph TD I[SUBMIT-APPROVAL2] --> S1{Application ID entered} S1 -- No --> S1E[ENTER APPLICATION ID] S1 -- Yes --> S2{Authority user code entered} S2 -- No --> S2E[AUTHORITY USER CODE IS REQUIRED] S2 -- Yes --> S3{Decision is A or R} S3 -- No --> S3E[DECISION MUST BE A=APPROVE OR R=REJECT] S3 -- Yes --> S4[PERFORM LOAD-APPLICATION] S4 --> S5{Message = APPLICATION LOADED} S5 -- No --> S5E[Exit with load message] S5 -- Yes --> S6{APPROVAL-1-STATUS = A} S6 -- No --> S6E[FIRST APPROVAL MUST BE GRANTED BEFORE SECOND] S6 -- Yes --> S7[PERFORM VALIDATE-AUTHORITY] S7 --> S8{Message = AUTHORITY USER VALIDATED} S8 -- No --> S8E[Exit with validation message] S8 -- Yes --> S9{Same authority as first approver} S9 -- Yes --> S9E[SECOND APPROVER MUST BE FROM DIFFERENT AUTHORITY] S9 -- No --> S10{Licence type authorised} S10 -- No --> S10E[AUTHORITY NOT AUTHORISED FOR THIS LICENSE TYPE] S10 -- Yes --> S11{Decision is A} S11 -- Yes --> S12[Status = AP] S11 -- No --> S13[Status = RE] S12 --> S14[UPDATE LICENSE_APPLICATION] S13 --> S14 S14 --> S15{Decision is A} S15 -- Yes --> S16[SECOND APPROVAL GRANTED - READY FOR LICENSE ISSUE] S15 -- No --> S17[SECOND APPROVAL REJECTED - APPLICATION CLOSED]

4.6.1 Decision Validation

COBOL 
IF DA2DECI = SPACES OR DA2DECI NOT IN ('A','R')
               MOVE 'DECISION MUST BE A=APPROVE OR R=REJECT' TO DA2MSG
               GO TO SUBMIT-A2-EXIT
           END-IF

4.6.2 First-Approval Prerequisite

COBOL 
IF APPROVAL-1-STATUS OF DCLDLIS-LICENSE-APPL NOT = 'A'
               MOVE 'FIRST APPROVAL MUST BE GRANTED BEFORE SECOND'
                   TO DA2MSG
               GO TO SUBMIT-A2-EXIT
           END-IF

4.6.3 Segregation of Duties

COBOL 
*    Segregation: second approver must differ from first
           IF AUTHORITY-NAME OF DCLDLIS-AUTH-USER = WS-APPROVAL1-AUTH
               MOVE 'SECOND APPROVER MUST BE FROM DIFFERENT AUTHORITY'
                   TO DA2MSG
               GO TO SUBMIT-A2-EXIT
           END-IF

4.6.4 Licence-Type Authorisation

COBOL 
*    Check license type authorisation
           IF DA2LTYO NOT IN LIC-TYPES-AUTH OF DCLDLIS-AUTH-USER
               MOVE 'AUTHORITY NOT AUTHORISED FOR THIS LICENSE TYPE'
                   TO DA2MSG
               GO TO SUBMIT-A2-EXIT
           END-IF

The licence-type test uses the screen output field DA2LTYO, which LOAD-APPLICATION fills. It is tested with NOT IN against the authority’s LIC-TYPES-AUTH string.

4.6.5 Status Derivation

COBOL 
MOVE DA2DECI TO WS-DECISION
           IF WS-DECISION = 'A'
               MOVE 'AP' TO APPLICATION-STATUS OF DCLDLIS-LICENSE-APPL
           ELSE
               MOVE 'RE' TO APPLICATION-STATUS OF DCLDLIS-LICENSE-APPL
           END-IF

4.6.6 Persisting the Second Approval

COBOL 
EXEC SQL
               UPDATE DLIS.LICENSE_APPLICATION SET
                   APPROVAL_2_STATUS    = :WS-DECISION,
                   APPROVAL_2_AUTHORITY = :AUTHORITY-NAME
                                          OF DCLDLIS-AUTH-USER,
                   APPROVAL_2_DATE      = CURRENT DATE,
                   APPROVAL_2_NOTES     = :DA2DCNTI,
                   APPLICATION_STATUS   = :APPLICATION-STATUS
                                          OF DCLDLIS-LICENSE-APPL,
                   LAST_UPDATED_DATE    = CURRENT DATE,
                   LAST_UPDATED_BY      = :DA2AUCOI
               WHERE APPLICATION_ID     = :APPLICATION-ID
                                          OF DCLDLIS-LICENSE-APPL
           END-EXEC

4.6.7 Outcome Message

COBOL 
IF WS-DECISION = 'A'
               MOVE 'SECOND APPROVAL GRANTED - READY FOR LICENSE ISSUE'
                   TO DA2MSG
           ELSE
               MOVE 'SECOND APPROVAL REJECTED - APPLICATION CLOSED'
                   TO DA2MSG
           END-IF

4.7 Application Status State Transition

stateDiagram-v2 [*] --> FirstApproved: First approval = A FirstApproved --> AP: Second decision A and all checks pass FirstApproved --> RE: Second decision R and all checks pass FirstApproved --> FirstApproved: Any check fails (no update) AP --> [*]: Ready for licence issuance RE --> [*]: Application closed

5. Paragraph Reference

Paragraph Role Key behaviour
MAIN-LOGIC Entry point Chooses first-time or re-entry path. Ends with STOP RUN.
INIT-SCREEN First-time display Sends the empty map and returns with TRANSID('DL09').
PROCESS-INPUT Re-entry dispatcher Receives the map, routes by PF key and re-sends with DATAONLY.
LOAD-APPLICATION F3 and reused by submit Reads application and candidate, fills the screen and saves WS-APPROVAL1-AUTH.
LOAD-APP-EXIT Exit Contains only EXIT.
VALIDATE-AUTHORITY F4 and reused by submit Validates an active level-2 authority user.
VALIDATE-AUTH-EXIT Exit Contains only EXIT.
SUBMIT-APPROVAL2 F1 Runs the guard chain, the update and the outcome message.
SUBMIT-A2-EXIT Exit Contains only EXIT.

The program uses GO TO to a dedicated exit paragraph as its early-termination path. After an error message is set, no further validation or update logic runs.

7. Constraints and Business Rules

7.1 Business Rule Summary

# Rule Paragraph Failure message
1 The authority user must be active (A) and at level 2. VALIDATE-AUTHORITY AUTHORITY USER NOT FOUND OR NOT ACTIVE AT LEVEL 2
2 The decision must be A or R. SUBMIT-APPROVAL2 DECISION MUST BE A=APPROVE OR R=REJECT
3 APPROVAL_1_STATUS must be A. SUBMIT-APPROVAL2 FIRST APPROVAL MUST BE GRANTED BEFORE SECOND
4 The second authority must differ from the first. SUBMIT-APPROVAL2 SECOND APPROVER MUST BE FROM DIFFERENT AUTHORITY
5 The licence type must be in LIC_TYPES_AUTH. SUBMIT-APPROVAL2 AUTHORITY NOT AUTHORISED FOR THIS LICENSE TYPE
6 Decision A gives AP. Any other decision (R) gives RE. SUBMIT-APPROVAL2 n/a
7 The second approval is recorded with status, authority, date, notes and audit user. SUBMIT-APPROVAL2 n/a
8 The outcome message depends on the decision. SUBMIT-APPROVAL2 n/a

7.2 Business Significance

  • Approver qualification. If it were weakened, inactive or first-level users could give final approval.
  • Segregation of duties. Without it, a single authority could approve at both levels. That removes dual control.
  • Licence-type scope. It stops an authority from approving licence types outside its remit.
  • Sequencing. It stops applications that never passed, or failed, the first level from being approved at the second.
  • Status mapping. An incorrect mapping would send rejected applications to licence issuance, or close approved ones.

7.3 Navigation and Technical Constraints

  • Only F1, F3, F4 and F12 are recognised. Any other key shows “USE F1 F3 F4 OR F12” and does no processing.
  • The COMMAREA is fixed at 350 bytes (PIC X(350), LENGTH(350)).
  • LAST_UPDATED_BY holds the authority user code typed on the screen, not the CICS signed-on user ID. The program does not cross-check the two.
  • Only A and R are accepted, so the only application statuses this program can write are AP and RE.

8. Error Handling

8.1 Error Categories

Category Handling Message
Missing application ID Exit through GO TO ENTER APPLICATION ID
Missing authority user code Exit through GO TO ENTER AUTHORITY USER CODE (validate) / AUTHORITY USER CODE IS REQUIRED (submit)
Invalid decision Exit through GO TO DECISION MUST BE A=APPROVE OR R=REJECT
Application not found (SQLCODE 100) Exit through GO TO APPLICATION NOT FOUND
Authority not found, inactive or wrong level Exit through GO TO AUTHORITY USER NOT FOUND OR NOT ACTIVE AT LEVEL 2
Workflow or business rule failure Exit through GO TO See section 7.1
Unrecognised PF key Default EVALUATE branch USE F1 F3 F4 OR F12

8.2 Error-Handling Approach

  • All feedback goes through the single DA2MSG field. It carries both error and success text.
  • Only one message is shown at a time. The first failing check wins.
  • Success messages are “APPLICATION LOADED”, “AUTHORITY USER VALIDATED”, “SECOND APPROVAL GRANTED - READY FOR LICENSE ISSUE” and “SECOND APPROVAL REJECTED - APPLICATION CLOSED”.
  • The map is re-sent after every action, so the user sees the result immediately.
  • The SUBMIT-APPROVAL2 paragraph reads the first-approval authority from the database again on every submit. The segregation check therefore does not depend on earlier screen state.
  • Every failure leaves the screen available for correction and resubmission. There is no retry loop or default substitution.

8.3 Gaps and Limitations

  • SQLCODE handling. Only SQLCODE = 100 is tested. Negative codes such as deadlock, timeout or authorisation errors are not detected on either SELECT.
  • Unchecked UPDATE. The update has no SQLCODE check. The “granted” or “rejected” message appears even if the update failed or changed no row.
  • Unchecked CICS responses. RESP values are stored in WS-RESP1 but never examined. MAPFAIL and terminal errors are not handled.
  • No exception handling or audit logging. There is no HANDLE CONDITION, HANDLE ABEND, explicit commit or rollback, or logging to a queue or file. The unit of work is committed by the final EXEC CICS RETURN.
  • Unused fields. SQLCA and the shared return code and message fields from the common copybook are declared but not used.
  • Transaction ID discrepancy. The program header says DL09. The mapping table in AGENTS.md lists this program as DL08.

9. Examples

9.1 Example 1: Successful Approval

Scenario: An authority user from a different body than the first approver approves a car licence application.

Screen field Value
DA2AIDI 1001
DA2AUCOI AUTH002
DA2DECI A
DA2DCNTI All checks clear

Database state before submission:

  • Application 1001: APPROVAL_1_STATUS = 'A', APPROVAL_1_AUTHORITY = 'City Transport Authority', APPLICATION_STATUS = 'A1', licence type C.
  • User AUTH002: level 2, active, AUTHORITY_NAME = 'State Roads Authority', LIC_TYPES_AUTH = 'CAB'.

Steps (F3, then F4, then F1):

  1. F3 loads the application and shows the candidate, the licence type and the first approver’s authority.
  2. F4 validates AUTH002 and shows State Roads Authority.
  3. F1 runs all guards and executes the UPDATE.

Result:

CODE 
SECOND APPROVAL GRANTED - READY FOR LICENSE ISSUE

The row now has APPROVAL_2_STATUS = 'A', APPROVAL_2_AUTHORITY = 'State Roads Authority', APPLICATION_STATUS = 'AP' and LAST_UPDATED_BY = 'AUTH002'.

All guards pass for these reasons:

  • The first approval is A.
  • The two authorities differ.
  • 'CAB' contains 'C'.

9.2 Example 2: Segregation-of-Duties Violation

Scenario: The second approver belongs to the same authority as the first.

  • Application 1002: APPROVAL_1_STATUS = 'A', APPROVAL_1_AUTHORITY = 'City Transport Authority'.
  • User AUTH003: level 2, active, AUTHORITY_NAME = 'City Transport Authority'.
  • Decision: A.

Result:

CODE 
SECOND APPROVER MUST BE FROM DIFFERENT AUTHORITY

AUTHORITY-NAME equals WS-APPROVAL1-AUTH, so the guard fires before any UPDATE. No database changes are made.

9.3 Example 3: First Approval Missing

Scenario: A user submits a second approval before the first approval has been granted.

  • Application 1003: APPROVAL_1_STATUS = ' '.
  • User AUTH004: valid level-2 user.
  • Decision: A.

Result:

CODE 
FIRST APPROVAL MUST BE GRANTED BEFORE SECOND

SUBMIT-APPROVAL2 exits through GO TO SUBMIT-A2-EXIT. It does not reach authority validation or the update.
