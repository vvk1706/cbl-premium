Payment Entry & Processing (DL07)

1. Overview

Payment Entry & Processing is the online fee-collection function of the Driver License Information System (DLIS). It runs as CICS transaction DL07 and is implemented by the COBOL program DLISPAY. Operators use BMS map DLISPE01 (mapset DLISPE) to do three things:

  • Look up a license application.
  • Record the initial license fee payment.
  • Print a receipt.

The program covers these areas:

Capability Description
Fee lookup Reads the applicant’s details and the active initial fee (FEE_TYPE = 'IF') for the license type from DB2.
Payment recording Inserts a row into DLIS.PAYMENT with status S and fee type IF.
Receipt number generation Builds the number as 'RCP' + current date (YYYYMMDD) + application ID.
Application status update Sets PAYMENT_STATUS = 'P' and APPLICATION_STATUS = 'PA' on DLIS.LICENSE_APPLICATION.
Receipt printing Delegated to program DLISRPRT through EXEC CICS LINK.

Before a payment is accepted, two business rules must pass:

  1. The applicant’s history check must be passed (HIST_CHECK_STATUS = 'P').
  2. The application must not already be paid (PAYMENT_STATUS must not be 'P').

1.1 Function Keys

Key Action Paragraph
F1 Validate and record the payment PROCESS-PAYMENT
F3 Look up the application and show the fee LOAD-APPLICATION
F5 Print the receipt PRINT-RECEIPT
F12 Exit the transaction PROCESS-INPUT (EXEC CICS RETURN)
Other Show USE F1 F3 F5 OR F12 PROCESS-INPUT

2. System Architecture

2.1 Component View

DLISPAY is a pseudo-conversational CICS/COBOL program. It uses BMS for terminal I/O and DB2 for persistence. It passes control to DLISRPRT for printing. State is carried between screen interactions in a 350-byte COMMAREA.

graph TD OP[Operator Terminal] --> BMS[BMS Map DLISPE01 / Mapset DLISPE] BMS --> TX[CICS Transaction DL07] TX --> PGM[DLISPAY COBOL Program] PGM -->|EXEC CICS LINK| RPT[DLISRPRT Receipt Print Program] PGM -->|EXEC SQL| DB2[(DB2 Subsystem DSN1)] DB2 --> T1[DLIS.LICENSE_APPLICATION] DB2 --> T2[DLIS.CANDIDATE] DB2 --> T3[DLIS.LICENSE_FEE_SCHEDULE] DB2 --> T4[DLIS.PAYMENT] DB2 --> T5[SYSIBM.SYSDUMMY1] PGM --> CA[DLIS-COMMAREA 350 bytes] CA --> TX

DLISPAY has no IBM MQ operations and no external file I/O.

2.2 Layers and Responsibilities

Layer Component Role
Presentation BMS map DLISPE01, mapset DLISPE Collects the application ID, payment method, reference and processed-by values. Displays the candidate, fee, receipt and message fields.
Transaction control CICS transaction DL07, EIBCALEN, EIBAID Separates first entry from re-entry and routes by function key.
Business logic DLISPAY paragraphs Validation, eligibility rules, receipt generation, payment recording and status advancement.
Data DB2 tables in schema DLIS Stores applications, candidates, fees and payments.
Output delegation DLISRPRT Formats and prints the receipt for the payment.

2.3 Program Structure

graph TD ML[MAIN-LOGIC] -->|EIBCALEN = 0| IS[INIT-SCREEN] ML -->|EIBCALEN > 0| PI[PROCESS-INPUT] PI -->|PF1| PP[PROCESS-PAYMENT] PI -->|PF3| LA[LOAD-APPLICATION] PI -->|PF5| PR[PRINT-RECEIPT] PI -->|PF12| EX([EXEC CICS RETURN]) PP -->|PERFORM| LA LA --> LAE[LOAD-APP-EXIT] PP --> PPE[PROCESS-PAY-EXIT] PR --> PRE[PRINT-RECEIPT-EXIT] PR -->|CICS LINK| DLISRPRT

Each routine has a dedicated exit paragraph (LOAD-APP-EXIT, PROCESS-PAY-EXIT, PRINT-RECEIPT-EXIT). Errors reach it with GO TO, so each routine has a single exit point.

3. Pseudo-Conversational Control Flow

3.1 Entry and Re-entry

MAIN-LOGIC is the entry point.

  • First invocation (EIBCALEN = 0): INIT-SCREEN does the following.
    1. Moves the first 10 characters of CURRENT-DATE to DPEDATE.
    2. Sends map DLISPE01 with ERASE and FREEKB.
    3. Issues EXEC CICS RETURN TRANSID('DL07') with the 350-byte COMMAREA.
  • Re-entry (EIBCALEN > 0): DFHCOMMAREA is moved into DLIS-COMMAREA, and PROCESS-INPUT runs.

PROCESS-INPUT receives the map and evaluates EIBAID. After the selected routine finishes, it re-sends the map with DATAONLY and FREEKB. It then returns to DL07 with the COMMAREA.

3.2 Interaction Sequence

sequenceDiagram participant Op as Operator participant CICS as CICS DL07 participant Pgm as DLISPAY participant Db as DB2 participant Rpt as DLISRPRT Op->>CICS: Start DL07 CICS->>Pgm: EIBCALEN = 0 Pgm-->>Op: Send empty map DLISPE01 with date Op->>Pgm: Enter application ID, press F3 Pgm->>Db: SELECT application and candidate Pgm->>Db: SELECT active IF fee Pgm-->>Op: Name, license type, fee, APPLICATION LOADED Op->>Pgm: Enter method, reference, processed by, press F1 Pgm->>Db: Reload application and fee Pgm->>Db: INSERT PAYMENT Pgm->>Db: SELECT IDENTITY_VAL_LOCAL Pgm->>Db: UPDATE LICENSE_APPLICATION Pgm-->>Op: Payment ID, receipt, PAYMENT RECORDED SUCCESSFULLY Op->>Pgm: Press F5 Pgm->>Rpt: EXEC CICS LINK with COMMAREA Rpt-->>Pgm: Return Pgm-->>Op: RECEIPT SENT TO PRINTER

3.3 Overall Processing Flow

graph TD A([Start DL07]) --> B{EIBCALEN = 0} B -- Yes --> C[INIT-SCREEN: send map with date] C --> D([RETURN TRANSID DL07]) B -- No --> E[Restore COMMAREA] E --> F[RECEIVE MAP DLISPE01] F --> G{EIBAID} G -- PF1 --> H[PROCESS-PAYMENT] G -- PF3 --> I[LOAD-APPLICATION] G -- PF5 --> J[PRINT-RECEIPT] G -- PF12 --> K([RETURN and end]) G -- Other --> L[Message: USE F1 F3 F5 OR F12] H --> M[SEND MAP DATAONLY] I --> M J --> M L --> M M --> N([RETURN TRANSID DL07 with COMMAREA])

4. Inputs

4.1 COMMAREA

DFHCOMMAREA is 350 bytes and is moved into DLIS-COMMAREA on every re-entry.

Field Purpose
CA-TRANSACTION-ID Owning transaction (DL07)
CA-CANDIDATE-ID Candidate carried across interactions
CA-APPLICATION-ID Application carried across interactions, available to DLISRPRT
CA-USER-ID Operator ID for audit and context
CA-ACTION Action code between cycles
CA-PAYMENT-ID New payment identifier relayed to the print program

4.2 Map Input Fields

Field Description
DPEAIDI Application ID. It is the primary key for the lookup and part of the receipt number.
DPEMETHI Payment method: CC, DC, EF, CS or CH.
DPEREFI Payment reference, such as a bank authorisation code.
DPEPRCBYI Processed-by operator or staff identifier.
DPERCTO Receipt number field. It is tested on F5 to confirm a payment was processed.

4.3 CICS System Values

  • EIBCALEN distinguishes first entry from re-entry.
  • EIBAID identifies the key pressed (DFHPF1, DFHPF3, DFHPF5, DFHPF12).
  • CURRENT-DATE supplies the screen date and the date part of the receipt number.

5. Fee Lookup (F3 – LOAD-APPLICATION)

5.1 Processing Steps

  1. If DPEAIDI is zeros, the message is ENTER APPLICATION ID and the routine exits.
  2. A DB2 join of DLIS.LICENSE_APPLICATION and DLIS.CANDIDATE retrieves CANDIDATE_ID, LICENSE_TYPE, HIST_CHECK_STATUS, PAYMENT_STATUS, FIRST_NAME and LAST_NAME.
  3. If SQLCODE = 100, the message is APPLICATION NOT FOUND and the routine exits.
  4. The full name is built with STRING (first name, space, last name) into DPECNAMO. The license type goes to DPELTYO, and its description goes to DPELDSO.
  5. A second SELECT reads the fee and currency from DLIS.LICENSE_FEE_SCHEDULE.
  6. If the fee is found (SQLCODE = 0), it is edited into WS-FEE-AMOUNT-D (ZZZ,ZZ9.99) and shown in DPEFEEO and DPECURRO.
  7. The message is APPLICATION LOADED.

The fee lookup uses these filters:

Criterion Value
License type Matches the application
FEE_TYPE 'IF' (initial fee)
ACTIVE_STATUS 'A'
EFFECTIVE_DATE <= CURRENT DATE
Row limit FETCH FIRST 1 ROW ONLY

If no fee row is found, the fee fields stay empty and the load still succeeds.

5.2 License Type Description

COBOL 
EVALUATE LICENSE-TYPE OF DCLDLIS-LICENSE-APPL
               WHEN 'L' MOVE 'LEARNER'   TO DPELDSO
               WHEN 'P' MOVE 'PROBATION' TO DPELDSO
               WHEN 'O' MOVE 'OPEN'      TO DPELDSO
           END-EVALUATE

There is no WHEN OTHER branch. For any other code, the description field is left unchanged.

5.3 Lookup Flow

graph TD A([F3 pressed]) --> B{Application ID entered} B -- No --> B1[ENTER APPLICATION ID] B -- Yes --> C[Join LICENSE_APPLICATION and CANDIDATE] C --> D{SQLCODE = 100} D -- Yes --> D1[APPLICATION NOT FOUND] D -- No --> E[Build name and license description] E --> F[Select active IF fee] F --> G{SQLCODE = 0} G -- Yes --> H[Show fee and currency] G -- No --> I[Leave fee fields empty] H --> J[APPLICATION LOADED] I --> J

6. Payment Recording (F1 – PROCESS-PAYMENT)

6.1 Validation Sequence

Checks run in this order. The first failure sets DPEMSG and goes to PROCESS-PAY-EXIT, so nothing is written to the database.

# Check Message on failure
1 Application ID not zeros ENTER APPLICATION ID
2 Payment method not blank PAYMENT METHOD IS REQUIRED
3 Method in CC, DC, EF, CS, CH INVALID PAYMENT METHOD
4 Payment reference not blank PAYMENT REFERENCE IS REQUIRED
5 LOAD-APPLICATION returns APPLICATION LOADED The message set by LOAD-APPLICATION is kept
6 HIST-CHECK-STATUS = 'P' HISTORY CHECK MUST BE PASSED BEFORE PAYMENT
7 PAYMENT-STATUS not 'P' PAYMENT ALREADY RECORDED FOR THIS APPLICATION

The reload in step 5 gets the latest application state and the fee before the insert.

6.2 Business Rule Code

COBOL 
IF HIST-CHECK-STATUS OF DCLDLIS-LICENSE-APPL NOT = 'P'
               MOVE 'HISTORY CHECK MUST BE PASSED BEFORE PAYMENT'
                   TO DPEMSG
               GO TO PROCESS-PAY-EXIT
           END-IF
COBOL 
IF PAYMENT-STATUS OF DCLDLIS-LICENSE-APPL = 'P'
               MOVE 'PAYMENT ALREADY RECORDED FOR THIS APPLICATION'
                   TO DPEMSG
               GO TO PROCESS-PAY-EXIT
           END-IF

6.3 Receipt Number Generation

The receipt number is 'RCP' + YYYYMMDD + application ID, stored in WS-RECEIPT-NUMBER (PIC X(20)).

COBOL 
*    Generate receipt number
           MOVE CURRENT-DATE(1:8)  TO WS-RECEIPT-DATE
           STRING 'RCP' WS-RECEIPT-DATE DPEAIDI
               INTO WS-RECEIPT-NUMBER

For example, application 1234567 on 2025-01-15 gives RCP202501151234567.

6.4 Payment Insert

Screen and application values are moved into the DCLDLIS-PAYMENT host variables. The row is then inserted with payment status 'S' and fee type 'IF'.

COBOL 
*    Insert payment
           MOVE DPEMETHI TO PAYMENT-METHOD    OF DCLDLIS-PAYMENT
           MOVE DPEREFI  TO PAYMENT-REFERENCE OF DCLDLIS-PAYMENT
           MOVE DPEAIDI  TO APPLICATION-ID    OF DCLDLIS-PAYMENT
           MOVE CANDIDATE-ID OF DCLDLIS-LICENSE-APPL
                         TO CANDIDATE-ID      OF DCLDLIS-PAYMENT
           MOVE LICENSE-TYPE OF DCLDLIS-LICENSE-APPL
                         TO LICENSE-TYPE      OF DCLDLIS-PAYMENT
           MOVE WS-FEE-AMOUNT TO PAYMENT-AMOUNT OF DCLDLIS-PAYMENT
           MOVE WS-RECEIPT-NUMBER TO RECEIPT-NUMBER OF DCLDLIS-PAYMENT
           MOVE DPEPRCBYI TO PROCESSED-BY OF DCLDLIS-PAYMENT
           EXEC SQL
               INSERT INTO DLIS.PAYMENT
                  (APPLICATION_ID, CANDIDATE_ID, PAYMENT_AMOUNT,
                   PAYMENT_METHOD, PAYMENT_REFERENCE, PAYMENT_STATUS,
                   LICENSE_TYPE, FEE_TYPE, RECEIPT_NUMBER, PROCESSED_BY)
               VALUES
                  (:APPLICATION-ID, :CANDIDATE-ID, :PAYMENT-AMOUNT,
                   :PAYMENT-METHOD, :PAYMENT-REFERENCE, 'S',
                   :LICENSE-TYPE, 'IF', :RECEIPT-NUMBER, :PROCESSED-BY)
               OF DCLDLIS-PAYMENT
           END-EXEC

If SQLCODE is not 0, the message is DATABASE ERROR ON PAYMENT INSERT and the routine exits before any update.

6.5 Payment ID Retrieval

After a successful insert, the generated identity value is read with IDENTITY_VAL_LOCAL() from SYSIBM.SYSDUMMY1. It is shown in DPEPIDO and carried to the print program as CA-PAYMENT-ID. This requires PAYMENT_ID to be an identity column in DLIS.PAYMENT.

6.6 Application Status Update

COBOL 
*    Update application
           EXEC SQL
               UPDATE DLIS.LICENSE_APPLICATION SET
                   PAYMENT_STATUS    = 'P',
                   PAYMENT_REFERENCE = :PAYMENT-REFERENCE
                                       OF DCLDLIS-PAYMENT,
                   APPLICATION_STATUS= 'PA',
                   LAST_UPDATED_DATE = CURRENT DATE,
                   LAST_UPDATED_BY   = :PROCESSED-BY OF DCLDLIS-PAYMENT
               WHERE APPLICATION_ID  = :APPLICATION-ID
                                       OF DCLDLIS-PAYMENT
           END-EXEC

The screen then shows the payment ID (DPEPIDO), receipt number (DPERCTO) and status S (DPEPSTSO). The message is PAYMENT RECORDED SUCCESSFULLY.

6.7 Payment Flow

graph TD A([F1 pressed]) --> B{ID, method, valid method, reference present} B -- No --> B1[Message and exit] B -- Yes --> C[PERFORM LOAD-APPLICATION] C --> D{APPLICATION LOADED} D -- No --> D1[Exit with load message] D -- Yes --> E{History check = P} E -- No --> E1[HISTORY CHECK MUST BE PASSED] E -- Yes --> F{Payment status = P} F -- Yes --> F1[PAYMENT ALREADY RECORDED] F -- No --> G[Build RCP + date + application ID] G --> H[INSERT PAYMENT status S, fee type IF] H --> I{SQLCODE = 0} I -- No --> I1[DATABASE ERROR ON PAYMENT INSERT] I -- Yes --> J[IDENTITY_VAL_LOCAL] J --> K[UPDATE application: PAYMENT_STATUS P, STATUS PA] K --> L[Show payment ID, receipt, status S] L --> M[PAYMENT RECORDED SUCCESSFULLY]

7. Receipt Printing (F5 – PRINT-RECEIPT)

Receipt formatting is delegated to DLISRPRT.

  1. If DPERCTO is blank, the message is PROCESS PAYMENT FIRST BEFORE PRINTING, and the LINK is skipped.
  2. Otherwise the program links to DLISRPRT with DLIS-COMMAREA (length 350).
  3. The message is RECEIPT SENT TO PRINTER.

The command takes this form:

COBOL 
EXEC CICS LINK PROGRAM('DLISRPRT')
                COMMAREA(DLIS-COMMAREA)
                LENGTH(350)
           END-EXEC

The COMMAREA carries CA-TRANSACTION-ID, CA-CANDIDATE-ID, CA-APPLICATION-ID, CA-PAYMENT-ID and CA-USER-ID, so the print program can retrieve and format the receipt.

sequenceDiagram participant Op as Operator participant Pay as DLISPAY participant Prt as DLISRPRT Op->>Pay: F5 alt Receipt number blank Pay-->>Op: PROCESS PAYMENT FIRST BEFORE PRINTING else Receipt number present Pay->>Prt: LINK with DLIS-COMMAREA Prt-->>Pay: Control returns Pay-->>Op: RECEIPT SENT TO PRINTER end

The LINK has no RESP or RESP2 option, so the success message is shown without confirming the print outcome.

10. Error Handling

10.1 Summary

Area Behavior
Input validation Fail-fast. The first failure sets a message and exits, with no database writes.
Application lookup Only SQLCODE = 100 is handled (APPLICATION NOT FOUND). Other SQL errors are not tested.
Fee lookup The fee is shown only when SQLCODE = 0. A missing fee is silently skipped. FETCH FIRST 1 ROW ONLY avoids SQLCODE -811.
Payment insert Any non-zero SQLCODE gives DATABASE ERROR ON PAYMENT INSERT, and the routine exits.
Identity retrieval and application update SQLCODE is not checked.
CICS SEND MAP and RECEIVE MAP RESP is stored in WS-RESP1 but never examined, so conditions such as MAPFAIL are ignored.
CICS LINK to DLISRPRT No RESP or HANDLE. Default CICS handling applies, which usually abends the task.
Unknown AID key Shows USE F1 F3 F5 OR F12.
Notifications All messages go to DPEMSG. There is no logging, ABEND, TD queue write or message colouring.

10.2 Known Risks

  • Possible inconsistency. The program has no SYNCPOINT ROLLBACK. If the insert succeeds and the application update fails, the payment exists but the application is not marked paid. The duplicate-payment check relies on that status, so a second payment could then be accepted.
  • Fragile failure detection. PROCESS-PAYMENT detects a failed reload by comparing DPEMSG with the text APPLICATION LOADED. Changing that wording would break the check.
  • Receipt field length. The receipt is 3 + 8 characters plus the application ID, stored in a 20-character field. A 10-digit application ID would give 21 characters and be truncated.

11. Dependencies

11.1 Runtime

  • CICS: transaction DL07, the DFHAID constants (DFHPF1, DFHPF3, DFHPF5, DFHPF12), and the EIB fields EIBCALEN and EIBAID.
  • BMS: mapset DLISPE and map DLISPE01. The symbolic map copybook is generated from the BMS source.
  • Called program: DLISRPRT, which must be defined in CICS and available in DLIS.LOADLIB.
  • DB2: subsystem DSN1, with SQLCA, CURRENT DATE and DCLGEN host structures. The CICS execution user needs read and write grants on the tables above.

11.2 Copybooks

Copybook Content
DLISWS Common working storage, messages and null indicators
DLISCSEC DLIS-COMMAREA layouts and CICS response areas
DLISDCLG DB2 host variable structures (DCLDLIS-PAYMENT, DCLDLIS-LICENSE-APPL and others)

11.3 Build and Deployment

Step Artifact
Compile and link jcl/DLISCOMP.jcl with proc/DLISCLNK.proc. Compiler IGYCRCTL with RENT,APOST,LIB,NOSEQ,NOTERM. Link-edit with IEWL using AMODE(31),RMODE(ANY).
DB2 precompile and bind DSNHPC, then jcl/DLISBIND.jcl (collection DLISPKG, plan DLISPLAN)
BMS assembly jcl/DLISBMS.jcl and proc/DLISBASM.proc
Schema db2/DLIS0001-CREATE-TABLES.sql, DLIS0002-CREATE-INDEXES.sql, DLIS0003-GRANTS.sql
CICS definitions csd/DLISCSD.csd (group DLISGRP)

The workspace documentation lists the payment transaction as DL06, but the program source uses DL07. Check the CSD definition for consistency.

11.4 Data Prerequisites

  • The application and candidate records must already exist (created by DLISCAND and DLISAPPL).
  • The history check must have run and passed.
  • An active IF fee row with an effective date on or before today must exist for the license type. Otherwise no fee is displayed, and the amount stays at its working-storage default.

Function Rule Outcome
License classification Map L, P, O to LEARNER, PROBATION, OPEN Readable license category on screen
