DLIS Application - Extract Business Rules Report

Business rules extraction workflow for the Driver License Information System (CICS / DB2 COBOL)

10 of 10 programs processed 73 business rules 50 paragraphs classified Output: docs/business-rule/cobol

Overview

Extracts and documents business logic from the selected programs as a functional overview and a rules inventory per program.

  • Extract business rules from COBOL, PL/I or HLASM programs
  • Analyze program structure and identify business-critical paragraphs
  • Generate structured documentation of business rules for modernization, documentation, or analysis

Workflow steps

  1. Prepare - 10 COBOL programs selected (all DLIS*.cbl transaction programs).
  2. Identify business rules - for each program, four passes were run:
    1. Variable extraction for the data dictionary
    2. Paragraph classification (business_critical or support_utility)
    3. Business rule extraction from the classified paragraphs
    4. Grouping of rules by function, sub-function and business rule (overview document)
  3. Workflow complete - overview and inventory documents written for every program.

Application lifecycle reflected in the rules

Application status codes set across the programs form a single workflow:

PE (DLISAPPL) → EC (DLISELIG) → HC (DLISHIST) → PA (DLISPAY) → A2 (DLISAP1) → AP (DLISAP2) → IS (DLISISSU)

RE (rejected) can be set by DLISELIG, DLISHIST, DLISAP1 and DLISAP2.

Business rules by program

DLISMENU - Main menu routing (4 rules)

Single entry point to the DLIS business functions. Validates the key and option, then transfers control with a 350-byte communication area.

  • Initial session detection and COMMAREA restoration - EIBCALEN = 0 shows a fresh menu; otherwise DFHCOMMAREA is restored into DLIS-COMMAREA before input is processed.
  • Attention key validation - only ENTER or PF12 are accepted; any other key redisplays the menu with guidance.
  • Mandatory option selection - a blank or low-values option is rejected with "PLEASE SELECT AN OPTION (1-10)".
  • Menu option routing - 1 and 2 → DLISCAND, 3 → DLISAPPL, 4 → DLISSTAT, 5 → DLISELIG, 6 → DLISHIST, 7 → DLISPAY, 8 → DLISAP1, 9 → DLISAP2, 10 → DLISISSU. Other values are rejected.
DLISSTAT - Application status inquiry (3 rules)

Read-only view of the processing stages of a license application.

  • Status inquiry request and key validation - ENTER runs the inquiry, PF12 exits, other keys show guidance; an Application ID is mandatory.
  • Lifecycle progress and stage result resolution - reads the application by ID, reports "APPLICATION NOT FOUND" on SQLCODE 100, translates status codes (PE, EC, HC, PA, A2, AP, IS, RE, else "UNKNOWN STATUS") and shows eligibility, history, payment and both approval stages.
  • Issued credential details resolution - license number and expiry date are read from DLIS.ISSUED_LICENSE only when the status is IS; the issued flag is YES only if the record is found.
DLISISSU - License issuance and printing (11 rules)

Officer-driven load, issue and print workflow (F3 / F1 / F6) for fully approved applications.

  • First-entry vs. returning transaction handling - preserves state across the multi-step pseudo-conversation.
  • Function key routing - F1 issue, F3 load, F6 print, F12 exit; other keys show "USE F1 F3 F6 OR F12".
  • Application ID presence - required before loading.
  • Display of pre-issuance gate statuses - candidate name, license type, eligibility, history, payment and both approvals are shown; message "APPLICATION LOADED".
  • Mandatory input validation - Application ID, vehicle class (A, B, C or D), issuing officer and issuing authority are required.
  • Approved-status gate - issuance only when APPLICATION-STATUS = 'AP'.
  • Expiry date and number prefix by license type - L: 1 year, LRN; P: 2 years, PRB; O: 5 years, OPN. Expiry keeps the current month and day.
  • License number generation - prefix + vehicle class + candidate ID + application ID.
  • Issued license record creation - insert into DLIS.ISSUED_LICENSE with status A and a demerit balance of 12.
  • Application closure and confirmation - application set to IS with audit fields; license number and expiry shown to the officer.
  • Print eligibility gate and invocation - printing requires a license number on screen, then links to DLISLPRT.
DLISAP2 - Second authority approval (8 rules)

Second-level approval or rejection with segregation of duties from the first approver.

  • Second-level authority eligibility - approver must be an active user (ACTIVE_STATUS = 'A') at authority level 2.
  • Authority independence from first approver - the second authority name must differ from the first.
  • License type authorization scope - the application license type must be within the authority's authorized types.
  • Valid decision required - only A (approve) or R (reject).
  • Two-level approval sequencing - first approval status must be A.
  • Application status derivation - A → AP, otherwise RE.
  • Persist second approval record - decision, authority, date, notes, new status and audit fields are updated.
  • Outcome message selection - "ready for license issue" or "application closed".
DLISAP1 - First authority approval (11 rules)

First-level approval (F1), application load (F3) and authority validation (F4).

  • New vs. returning session handling and function key routing - F1 submit, F3 load, F4 validate authority, F12 exit.
  • Application identification and retrieval - Application ID required; joined read of application and candidate; "APPLICATION NOT FOUND" guard.
  • Display of application details for approver - candidate name, license type, status, eligibility, history, payment status and reference.
  • Active level-1 authority validation - user code required; user must be active at authority level 1.
  • Mandatory input validation - Application ID, authority user code and decision (A/R).
  • Payment completion gate - PAYMENT-STATUS must be P.
  • License type authorization - license type must be in the authority's authorized list.
  • Status determination - A → A2 (forward to second approval); R → RE.
  • Persistence and audit trail - approval 1 status, authority, date, notes, application status and last-updated fields.
  • Outcome confirmation - forwarded for second approval, or rejected and closed.
DLISPAY - Payment entry and processing (5 rules)

Records the initial license fee payment and advances the application.

  • Derive license type description - L LEARNER, P PROBATION, O OPEN; no fallback for other values.
  • Enforce payment preconditions - history check status must be P; payment status P blocks duplicate payments.
  • Issue standardized receipt number - RCP + current date (YYYYMMDD) + application ID.
  • Record initial fee payment - insert into DLIS.PAYMENT with status S and fee type IF.
  • Mark application as paid - payment status P, application status PA, payment reference and audit fields.
DLISHIST - Driving history check (12 rules)

Loads the candidate's driving incidents, derives risk indicators and records a pass or fail result (F1 check, F3 load, F7/F8 scroll).

  • Initial vs. returning session handling and function key routing - F7 scrolls back 7 rows (floor of 1), F8 scrolls forward 7 rows.
  • Application ID required - applies to both load and history check.
  • Retrieve and display application and candidate details - joined read; "APPLICATION NOT FOUND" guard; full name and license type shown.
  • Demerit point accumulation - up to 50 incidents retained for display; all demerit points are totalled.
  • Active suspension or disqualification detection - incident types SU/DQ with an end date of today or later, or blank, set the suspension flag.
  • Outstanding unpaid fine detection - fine amount greater than 0 with paid status N.
  • Summary indicators shown for review - demerit total, suspension flag and fine flag.
  • Eligibility must be passed first - ELIG-CHECK-STATUS must be P.
  • Prioritised failure evaluation - (1) active suspension, (2) total demerit points over 12, (3) unpaid fines. Only the first reason is recorded.
  • Assign outcome and advance status - fail → history F and application RE; pass → P and HC. Result, date, notes and audit fields are persisted.
  • Present final result - "HISTORY CHECK PASSED" or the specific failure reason.
DLISELIG - Eligibility check (3 rules)

Age and license progression checks, executed in a single business-critical paragraph (RUN-ELIGIBILITY-CHECK).

  • Age calculation and minimum age enforcement - age = current year minus birth year (month and day ignored). Minimum age: Learner 16, Probation 17, Open 18.
  • Prior license holding requirement - evaluated only if the age check passed. Probation requires an active Learner license; Open requires an active Probation license.
  • Eligibility outcome and persistence - fail → eligibility F and application RE; pass → P and EC. Status, date, notes and checking user are stored.
DLISAPPL - License application entry (7 rules)

Candidate lookup (F3), fee display (F5) and application submission (F1).

  • Initial vs. re-entry session routing - restores the COMMAREA and records the transaction ID.
  • Function key routing - F1 submit, F3 lookup, F5 fee, F12 exit; other keys show "USE F1 F3 F5 OR F12".
  • Candidate ID presence, existence and active status - ID required; "CANDIDATE NOT FOUND" on SQLCODE 100; record status I is rejected.
  • Active initial fee schedule lookup - license type required; fee type IF, active, effective today (expiry null or on or after today); first row only; "NO FEE SCHEDULE FOR THIS LICENSE TYPE" if none.
  • Mandatory field and domain validation - candidate ID and license type required; license type must be L, P or O.
  • Duplicate application prevention - one active application per candidate and license type; statuses RE and IS are not counted as active.
  • Insert application as pending - status PE, terminal ID as creator; the generated application ID is shown with a success message.
DLISCAND - Candidate maintenance (9 rules)

Candidate lifecycle: create (F1), update (F2), inquire (F3) and deactivate (F4).

  • First-time vs. return entry determination and function key mapping - invalid keys show "INVALID KEY - USE F1-F4 OR F12".
  • Mandatory identity fields - first name, last name and national ID are required to create a candidate.
  • Duplicate active candidate prevention - an active (A) record with the same national ID blocks creation; inactive records do not.
  • Create active candidate with audit stamp - status A, terminal ID as creator; the generated candidate ID is shown.
  • Update with mandatory target - Candidate ID required; name, address, contact details and record status are updated together; not-found and database-error messages are returned.
  • Logical deactivation - sets record status to I; no physical delete, so history is preserved.
  • Search key requirement for inquiry - Candidate ID or National ID is required.
  • Candidate retrieval and profile presentation - looked up by either key (first row only); full profile and status are displayed.

Output files

Two documents were generated per program in docs/business-rule/cobol:

  • Overview - purpose of the program, grouped by business function, sub-function and business rule.
  • Inventory - every business rule in order of appearance, with code snippets and variable tables.

Data dictionary entries were also extracted for each program during the workflow.
