📋 1. Executive Summary

Change Description: Add a Vehicle Class field (A=Motorcycle, B=Light, C=Heavy, D=Bus) to the license application process. Currently Vehicle Class is entered only at issuance time in DLISISSU. This change captures it at application entry (DLISAPPL / DL03), persists it in DLIS.LICENSE_APPLICATION, propagates it through the CICS COMMAREA to all downstream programs, and retains it at issuance in DLIS.ISSUED_LICENSE.

Business Value: Regulatory compliance requires vehicle class to be declared and validated at application time. Early capture allows eligibility and approval reviewers to see the intended class, reduces the risk of a class mismatch between application and issued license, and lays the foundation for future fee-schedule differentiation by vehicle class.

⚠️ Key Risk 1

COMMAREA expansion requires simultaneous recompile and deployment of all 7 CICS programs — partial deployment causes storage overlay abends.

⚠️ Key Risk 2

In-flight applications will have NULL in the new VEHICLE_CLASS column — a migration UPDATE must run before go-live.

⚠️ Key Risk 3

The ISSUED_LICENSE.VEHICLE_CLASS NOT NULL constraint means DLISISSU must guarantee a non-blank value from COMMAREA or screen before INSERT.

Key Findings

ISSUED_LICENSE already has VEHICLE_CLASS. The DLIS.ISSUED_LICENSE table already contains VEHICLE_CLASS CHAR(2) NOT NULL with CHECK (VEHICLE_CLASS IN ('A','B','C','D')). DLISISSU.cbl already validates and inserts this field from the screen. The change adds it to upstream stages.
COMMAREA layout note. DLIS-APPL-COMMAREA currently ends at CA-LICENSE-NUMBER PIC X(20). Appending CA-VEHICLE-CLASS PIC X(2) is safe — no existing field offsets shift. The EXEC CICS RETURN LENGTH(350) literals in all programs must be verified to cover 352 bytes or updated accordingly.

Assumptions

  • Vehicle Class captured at application will always match the class stored in ISSUED_LICENSE — DLISISSU will prefer COMMAREA value
  • Existing in-flight applications (status not IS or RE) will receive default Vehicle Class 'C' via migration UPDATE before go-live
  • The append-only COMMAREA change keeps all 7 programs on the same byte layout after recompile

Constraints

  • All 7 COBOL programs must compile and deploy together — partial deployment will cause COMMAREA layout misalignment and CICS abends
  • DB2 Bind step must be rerun for DLISAPPL and DLISISSU after DBRM members are updated
  • BMS reassembly must complete before COBOL compilation to supply updated DSECT copybooks

⚠️ 9. Risks & Mitigations
🔴 HIGH — Partial Deployment: Mismatched COMMAREA Layout

Description: If any of the 7 programs is deployed with the old copybook while others use the new layout, CICS task storage will be misaligned, causing ASRA (storage protection) or AEIP abends.

Mitigation: Enforce a single coordinated build and deployment using jcl/DLISCOMP.jcl for all 7 programs; activate all new load modules via CICS PHASEIN in one step.

Contingency: CICS NEWCOPY old load modules immediately; revert copybooks and recompile.

🔴 HIGH — In-flight Application Rows Missing VEHICLE_CLASS

Description: Applications already in DB2 will have NULL VEHICLE_CLASS after the ALTER. DLISISSU will read COMMAREA but COMMAREA will also be empty for old sessions — the NOT NULL constraint on ISSUED_LICENSE will cause INSERT failure.

Mitigation: Run migration UPDATE inside a DB2 unit of recovery before go-live. Add a null guard in DLISISSU: if CA-VEHICLE-CLASS = SPACES, use DLIVCLSI from screen; fail with message if both are blank.

🟡 MEDIUM — BMS Screen Row Position Conflict

Description: Adding DAEVCLS at row 9, col 20 of DLISAE01 may conflict with existing screen layout if rows are already occupied.

Mitigation: Test assembled BMS on a 3270 emulator before COBOL compilation; verify row 9 is free in current map layout.

🟡 MEDIUM — DB2 Bind Failure After DBRM Update

Description: If DLISBIND.jcl is not run after recompile, the plan may use stale DBRMs that reference the old table layout.

Mitigation: Include DB2 Bind as a mandatory step immediately after DLISCOMP.jcl completes; verify plan name DLISPLAN is current.

🚀 11. Rollout & Operational Plan

Deployment Sequence

  1. Commit all source changes to version control; peer review completed
  2. Execute db2/DLIS0004-ALTER-VEHICLE-CLASS.sql against DSN1 subsystem
  3. Run migration UPDATE; validate row counts in DB2
  4. Run jcl/DLISBMS.jcl — assemble DLISAE mapset; confirm DSECT in DLIS.COPYBOOK
  5. Run jcl/DLISCOMP.jcl — compile all 7 programs simultaneously
  6. Run jcl/DLISBIND.jcl — bind DLISAPPL and DLISISSU DBRMs into DLISPKG/DLISPLAN
  7. CICS PHASEIN all new load modules atomically (or controlled CICS restart in lower environment)
  8. Smoke test: DL03 → submit with Vehicle Class B → verify DB2 row → DL09 → issue → verify ISSUED_LICENSE

Rollback Procedure

Rollback Triggers
  • ASRA or AEIP abends in any DLIS transaction after deployment
  • DB2 INSERT failure due to Vehicle Class constraint
  • BMS map corruption causing terminal errors
  1. CICS PHASEIN old load modules from DLIS.LOADLIB backup
  2. Restore pre-change DSECT copybooks to DLIS.COPYBOOK from backup
  3. Recompile all 7 programs from pre-change COBOL + copybooks
  4. CICS PHASEIN reverted load modules
  5. If DB2 issues persist: ALTER TABLE DLIS.LICENSE_APPLICATION DROP COLUMN VEHICLE_CLASS (requires REORG)
